# บันทึกการไล่ปัญหาจอ ST7789 — แยกสิ่งที่วัดจริง ออกจากสิ่งที่เดา

เขียน 14 กันยายน 2026 เพื่อส่งให้ผู้ช่วยอีกตัว (Codex) อ่านประกอบก่อนตัดสินใจเรื่อง slip ring
ผู้เขียนคือ Claude ซึ่งเป็นคนเสนอทางแก้ส่วนใหญ่ในบันทึกนี้ และเป็นคนเดาผิดหลายข้อในหมวด C ด้วย
**อย่าเชื่อหมวด C และอย่าเชื่อข้อเสนอท้ายเอกสารโดยไม่ตรวจ** เจ้าของงานต้องการความเห็นที่สอง

---

## 0. ฮาร์ดแวร์ที่ใช้

| รายการ | ค่า |
|---|---|
| บอร์ด | ESP32-S3-Zero (ESP32-S3FH4R2) USB CDC ในตัว ไม่มีชิป USB-UART แยก |
| จอ | ST7789 240×240 IPS โมดูล 8 ขา `GND VCC SCL SDA RST DC CS BL` |
| จำนวนจอ | ซื้อมา 6 เสีย 1 เหลือใช้งาน 5 ไม่มีสำรอง |
| ไลบรารี | Adafruit ST7789 / Adafruit GFX |
| บัสร่วม | SCK=GPIO12, MOSI=GPIO11, DC=GPIO9, RST=GPIO10 |
| CS แยกจอ | px=8, nx=13, py=4, ny=5, pz=6 (nz=17 เป็น placeholder ไม่มีจอ) |
| BL | ปล่อยลอย โมดูลนี้ป้อนไฟ backlight จาก VCC ผ่าน R บนบอร์ดจออยู่แล้ว |
| ไฟจอ | ตอนนี้กินจาก ขา 3V3 ของ ESP32 |

## A. สิ่งที่ยืนยันแล้ว — มีการวัดหรือเห็นผลจริง

### A1. จอกลับมาติดหลังเปลี่ยนสายจัมเปอร์ และเปลี่ยนเบรดบอร์ด
ลำดับเหตุการณ์ที่บันทึกได้:

1. เทสจอเดี่ยวครั้งแรกสุด (ก่อนรื้อทำหลายจอ) **ติด** ที่ SPI 24 MHz
2. หลังต่อหลายจอ จอดำหมด ต่อมาเหลือขึ้นจอเดียว แล้วดำหมดอีก
3. ช่วงที่ดำ **backlight ติดครบทั้ง 5 จอ** แปลว่า VCC/GND ถึงจอทุกใบ ปัญหาอยู่ที่สายสัญญาณล้วน
4. วัดแรงดันที่ปลายสายฝั่งจอ ตอนเฟิร์มแวร์กำลังแกว่งขาขึ้นลง: VCC 3.3 V, RST 3.3 V, **DC ค้างอยู่ 0.12–0.18 V ไม่แกว่งตาม** และ SDA ก็ไม่แกว่งเช่นกัน
5. ผู้ใช้เปลี่ยนสายจัมเปอร์ → ไฟเริ่มสลับตามได้ 2 เส้น แต่ภาพยังไม่ขึ้น
6. ผู้ใช้ **เปลี่ยนเบรดบอร์ด** (ไม่ได้บัดกรีใหม่) → **จอขึ้น**

**ข้อสรุปที่หลักฐานรองรับ: อาการดำเกิดจากหน้าสัมผัสไม่ถึง — สายจัมเปอร์เสีย และเบรดบอร์ดไม่จับ** ไม่ใช่ปัญหาโค้ด ไม่ใช่จอพัง ไม่ใช่ไฟไม่พอ

### A2. ไม่มีขาไหนช็อตกัน
เขียนคำสั่ง `scan_shorts` ลงเฟิร์มแวร์ ให้บอร์ดไล่ขับขาทีละขาเป็น HIGH ส่วนขาอื่นตั้งเป็น INPUT_PULLDOWN แล้วอ่านกลับ
**ผลคือไม่พบคู่ที่ช็อตกันเลย** ส่วนที่ RST อ่านได้ 3.3 V ค้าง อธิบายได้ด้วย pull-up ภายในโมดูลจอเอง ไม่ใช่ช็อต

### A3. บอร์ดไม่ได้รีเซ็ตตัวเองระหว่างใช้งาน
เฝ้าดูพอร์ต 60 วินาที ได้ **boot 1 ครั้ง, หลุด 0 ครั้ง, ข้อความ state 205 ข้อความ**
เสียงติ๊ด ๆ ที่ได้ยินเกิดตอนแฟลชและตอนเปิดพอร์ตเท่านั้น ซึ่งเป็นธรรมชาติของบอร์ดที่ใช้ USB ในตัว
เพราะ USB ของ ESP32-S3 อยู่ในชิปเดียวกับ CPU พอชิปรีเซ็ต พอร์ตจึงหายไปแล้วโผล่ใหม่ — บอร์ดที่มีชิป USB-UART แยก (CH340/CP2102) จะไม่มีอาการนี้
**นี่ไม่ใช่อาการเสีย และการเดินสายยาวขึ้นไม่เกี่ยวกับเรื่องนี้**

### A4. ต้องยก DTR ขึ้น ไม่งั้นบอร์ดเงียบ
ตอนแรกตั้ง `dtr=False, rts=False` เพื่อกันบอร์ดรีเซ็ต ผลคือบอร์ดไม่ส่งอะไรมาเลย
ค่าที่ใช้งานได้จริงคือ **`dtr=True, rts=False`** (RTS คือขารีเซ็ต) ยืนยันด้วยการเปิดพอร์ตสองครั้งแล้ว session เดิมยังอยู่ = ไม่รีเซ็ต

### A5. การแฟลชต้องใช้ค่านี้เท่านั้น
`upload_speed = 115200` และ `upload_flags = --no-stub`
ถ้าไม่ใส่ จะค้างที่ "Changing baud rate to 460800" หรือค้างที่ stub loader

### A6. สีของจอกลับด้าน ต้องเปิด INVON
พอจอขึ้นแล้ว ผู้ใช้รายงานว่า **ปลาเป็นสีฟ้า ทะเลเป็นสีส้ม ๆ ไข่ ๆ** ซึ่งคือภาพกลับสีชัดเจน
แก้โดยตั้ง `inversion = true` ทั้ง 6 หน้าใน `kFaces` เป็นพฤติกรรมปกติของจอ IPS ST7789 รุ่นนี้
**สถานะ: แฟลชแล้ว แต่ยังไม่ได้รับการยืนยันจากผู้ใช้ว่าสีถูกต้องหรือยัง**

### A7. ไฟจากพอร์ต USB โน้ตบุ๊กไม่พอ — เอกสารของโปรเจกต์เองเตือนไว้ก่อนแล้ว
ผู้ใช้สังเกตเอง: **"ตอนอัปโหลดมันติด ๆ หลุด ๆ เหมือนแย่งพอร์ตกัน แต่ตอนเสียบอแดปเตอร์มันติดปกติ"**

`oceanX/output/procurement/cube-prototype.md` เขียนเตือนไว้ตั้งแต่ก่อนประกอบว่า:
> ต่อจอเกิน 2–3 ใบ ย้ายไปหัวชาร์จผนังทันที ใช้คอมเฉพาะตอนแฟลช — พอร์ต USB คอมจ่ายได้ 500mA (2.0) / 900mA (3.0)
> เกินแล้วจอวูบ / ESP32 รีเซ็ต / **เสียเวลาไล่บั๊กในโค้ดที่ไม่ได้ผิด**

อาการที่ผู้ใช้เห็นตรงกับที่เอกสารทำนายไว้ทุกตัวอักษร และ**เวลาที่เสียไปกับการไล่บั๊กในโค้ดก็ตรงกับที่เตือนไว้ด้วย**
สิ่งนี้ยังไม่ได้วัดเป็นตัวเลข แต่เป็นการสังเกตตรงของผู้ใช้ ไม่ใช่การเดาของ Claude

## B. สิ่งที่แก้ไปแล้ว แต่ยังพิสูจน์ไม่ได้ว่าจำเป็น

ทั้งหมดนี้ถูกใส่เข้าไป **ระหว่างที่สายยังเสียอยู่** จึงไม่มีทางรู้ว่าอันไหนช่วย อันไหนไม่เกี่ยว
หลังสายซ่อมแล้วยังไม่เคยถอดออกทีละอย่างเพื่อทดสอบ

### B1. ลดความเร็ว SPI จาก 10 MHz เหลือ 4 MHz
`kSpiClockHz` ใน `firmware/include/deep_sphere_config.h` บรรทัด 61
เหตุผลตอนนั้นคือ "เห็นพิกเซลเพี้ยนที่ 10 MHz" แต่ตอนที่เห็นพิกเซลเพี้ยน **สายยังเสียอยู่**
จอเดี่ยวใบแรกสุดเคยวิ่ง 24 MHz ได้สบาย
**นี่คือค่าที่น่าจะถอยกลับได้ และควรทดสอบเป็นอันดับแรก**

### B2. ยิงคำสั่ง ST7789 ซ้ำเองหลัง `init()`
ใน `setupDisplays()` ยิง SWRESET(0x01) → SLPOUT(0x11) → COLMOD(0x3A=0x55) → NORON(0x13) → DISPON(0x29) พร้อม delay
เหตุผลตอนนั้น: `init()` ของ Adafruit วิ่งที่ความเร็วดีฟอลต์ของไลบรารีเอง ไม่สนใจ `setSPISpeed()` ที่เรียกทีหลัง จึงกลัวว่าลำดับ init จะไม่ผ่าน
**ยังไม่เคยลองเอาออกหลังสายซ่อม** อาจไม่จำเป็นเลย

### B3. ปรับสีพื้นน้ำให้สว่างขึ้น
`config/live_ocean.json` → `background_keyframes`
เหตุผลตอนนั้นคือ "จอจริงอ่านเป็นดำ" แต่ช่วงนั้นสายยังเสีย และสียังกลับด้าน (ยังไม่ได้เปิด INVON)
**เหตุผลเดิมจึงอาจไม่ถูกต้อง** สีชุดนี้ควรตัดสินใหม่หลังยืนยัน A6

### B4. ตัวป้องกัน PSRAM
`buildMixTable()` อ่านค่ากลับทุกตัวหลังเขียน ถ้าไม่ตรงจะทิ้งตารางแล้วคำนวณทีละพิกเซลแทน
เป็นการกันไว้เฉย ๆ **ไม่เคยพบว่ามันทำงานจริง**

## C. สิ่งที่เดา และเดาผิด — Claude เป็นคนพูดเอง

บันทึกไว้ให้ครบ เพราะถ้าเห็นแค่ข้อสรุปจะดูน่าเชื่อกว่าความเป็นจริง

### C1. อ้างว่า SDA กับ RST ช็อตกัน — ผิด
`scan_shorts` ของบอร์ดเองบอกว่าไม่มีคู่ช็อต ค่า 3.3 V ที่ RST มาจาก pull-up ในโมดูลจอ

### C2. กล่าวหาว่าเสียบสายซ้อนแถวเดียวกันบนเบรดบอร์ด — ผิดและไม่สุภาพ
ไม่มีหลักฐานใด ๆ ผู้ใช้ปฏิเสธ และผู้เขียนถอนคำพูดแล้ว

### C3. อ้างว่า "สายยาวทำให้จอพัง" — ผิดตั้งแต่การใช้คำ
ไม่เคยอ้างงานวิจัยใด และไม่มีงานวิจัยรองรับประโยคนี้ เพราะประโยคนี้ผิดโดยตัวมันเอง
**ความยาวสายไม่ทำให้จอเสียหาย** สิ่งที่เกิดได้จริงคือสัญญาณเพี้ยนจนปลายทางอ่านผิด (signal integrity)
ซึ่งเป็นคนละเรื่องกับคำว่า "พัง" และ **ไม่เคยทดสอบกับชุดนี้หลังซ่อมสายเลย**

ส่วนที่เป็นความรู้วิศวกรรมทั่วไปจริง และอยู่ในเอกสารจัดซื้อของโปรเจกต์นี้มาก่อนแล้ว คือ
สายสัญญาณนาฬิกาที่ไม่มีตัวต้านทานปลายทางจะเกิดการสะท้อนกลับ ทำให้ขอบสัญญาณแกว่ง
`oceanX/output/procurement/cube-prototype.md` ระบุให้ใส่ **R อนุกรม 22–33 Ω ที่ SCLK ทุกบัส** เพื่อกัน ringing ไว้แล้ว
พร้อมเหตุผลว่า "ringing บนสายมือบัดกรี → ทำไมจอใบที่ 3 เพี้ยน"
**แต่ความรู้ทั่วไปข้อนี้ไม่ใช่หลักฐานว่ามันเกิดกับเรา** และข้อมูลที่วัดได้ชี้ไปที่หน้าสัมผัสล้วน ๆ

ที่สำคัญกว่านั้น: เอกสารเดียวกันตั้งเป้า SPI ไว้ที่ **26.6 MHz และถือ 40 MHz เป็นโบนัส**
Claude ลดลงเหลือ 4 MHz คือ **ต่ำกว่าเป้าของโปรเจกต์เองราว 7 เท่า** โดยไม่มีการวัดรองรับ

### C4. โหมดเทสขาชุดแรกมีจุดบอด
เวอร์ชันแรกขับทุกขาพร้อมกัน ทำให้สายที่เสียบผิดตำแหน่ง **ยังวัดได้ปกติ** เพราะขาข้างเคียงก็แกว่งเหมือนกัน
แก้ด้วยคำสั่ง `hold_pin` ที่ขับทีละขาเท่านั้น

## D. สิ่งที่ยังไม่รู้ — ยังไม่เคยทดสอบ

| หัวข้อ | สถานะ |
|---|---|
| เพดานความเร็ว SPI จริงของชุดนี้ | **ไม่รู้** หลังซ่อมสายยังไม่เคยลองเกิน 4 MHz |
| ต่อครบ 5 จอพร้อมกันแล้วรอดไหม | **ไม่รู้** ตอนนี้ต่ออยู่จอเดียว |
| ไฟ 3V3 ของ ESP32 พอเลี้ยง 5 จอไหม | **ไม่รู้** ค่า 0.01 A ที่เคยวัด อยู่บนย่าน 10 A ซึ่งหยาบเกินไปสำหรับโหลดระดับ 10–20 mA ใช้อ้างอิงไม่ได้ |
| คำสั่ง init ที่ยิงเองใน B2 จำเป็นไหม | **ไม่รู้** |
| สีถูกต้องหรือยังหลังเปิด INVON | **รอผู้ใช้ยืนยัน** |

**ลำดับทดสอบที่ควรทำ (ทีละอย่าง เปลี่ยนทีละตัวแปร):**
1. ดัน `kSpiClockHz` เป็น 10 MHz → ดูว่าภาพยังคมไหม
2. ถ้าผ่าน ดันเป็น 24 MHz → ดูอีกครั้ง
3. ต่อจอเพิ่มทีละใบจนครบ 5 **โดยจ่ายไฟจากหัวชาร์จผนัง ไม่ใช่พอร์ตโน้ตบุ๊ก** ตามข้อ A7 แล้ววัดแรงดันที่จอใบไกลสุดตอนติดครบ
4. วัดกระแสรวมบนย่าน mA ไม่ใช่ย่าน 10 A
5. ใส่ 100nF ที่ VCC ของทุกจอ ตามที่เอกสารจัดซื้อสั่งไว้ ก่อนสรุปว่าไฟพอหรือไม่พอ

## E. โจทย์ slip ring ที่อยากได้ความเห็นที่สอง

### E0. แบบที่ยังมีผลอยู่ตอนนี้ — และไม่มีบอร์ดที่สอง

**แก้ไข 14 ก.ย. 2026:** ฉบับแรกของเอกสารนี้อ้าง "แบบบอร์ดสองตัว + UART ผ่าน slip ring" เป็นทางเลือก
**นั่นผิด** เจ้าของงานทักท้วงว่าไม่ได้ทำแบบนั้นแล้ว และตรวจสอบแล้วพบว่าถูกต้อง
แบบนั้นอยู่ใน `one-week-prototype-bom.md` ซึ่ง **ถูกล้มไปตั้งแต่ 6 ก.ย.** และตัวที่มาแทนคือ `thursday-8-screen-bom.md`
ก็ **ถูกล้มต่อในวันที่ 7 ก.ย.** เช่นกัน — ทั้งสองฉบับตายแล้ว ไม่ควรใช้อ้างอิงเรื่องการออกแบบ

สายที่ยังมีผล:

| เอกสาร | สถานะ |
|---|---|
| `one-week-prototype-bom.md` | ❌ ตาย 6 ก.ย. (ที่นี่คือที่มาของ "บอร์ดสองตัว + UART") |
| `thursday-8-screen-bom.md` | ❌ ตาย 7 ก.ย. (แบบทรงเพชร 8 จอ) |
| **`cube-prototype.md`** (7 ก.ย.) | ✅ **ใช้อยู่** — แบบลูกบาศก์ 6 จอ และเป็นที่มาของคำเตือนฮาร์ดแวร์ใน E0.1, A7, C3 |
| **`cube-review-5000-plan.md`** (7 ก.ย.) | ✅ **ใช้อยู่** — ขอบเขตและงบ |

**แบบที่ใช้อยู่จริงตอนนี้ ตาม `cube-prototype.md` + `cube-review-5000-plan.md`:**

- **ESP32-S3-Zero อยู่บนถาดหมุนใต้ลูกบาศก์ หมุนไปพร้อมจอ** มีบอร์ดตัวเดียว ไม่มีบอร์ดที่สอง
- **สายจอทั้ง 6 ชุดไม่ข้ามรอยหมุนเลย** เดินจากลูกลงถาดบอร์ดไปด้วยกัน
- สิ่งที่ข้ามรอยหมุนมีแค่ **USB/ไฟเข้า** และสายจากของที่อยู่นิ่ง (AS5600, ล้อ, ปุ่ม)
- **ไม่ต้องซื้อ slip ring** — ใช้ **ช่องเดินสายที่ฐาน + หมุนไป–กลับแบบมีขีดจำกัด + ตัวหยุดทางกล**
- `cube-review-5000-plan.md` ระบุด้วยว่า **งบไม่ได้กันเงินไว้ซื้อ slip ring**

**ดังนั้นโจทย์จริงคือ:** เจ้าของงานกำลังจะ**เปลี่ยนจากแบบที่เอกสารวางไว้**
จาก "บอร์ดหมุนตาม + ไม่มี slip ring + หมุนจำกัดรอบ"
ไปเป็น "บอร์ดอยู่ฐาน + slip ring 12 เส้น + SPI ข้ามหน้าสัมผัส"
ซึ่งเป็นเรื่องใหม่ ไม่มีแบบเดิมรองรับ และเป็นเหตุผลที่ต้องการความเห็นที่สอง

**หมายเหตุความน่าเชื่อถือ:** Claude อ้างเอกสารที่ตายแล้วเป็นหลักฐาน แล้วเจ้าของงานเป็นคนจับได้เอง
ถือเป็นความผิดพลาดซ้ำรูปแบบเดียวกับหมวด C คือ **ยืนยันหนักแน่นเกินกว่าหลักฐานที่มี**

### E0.1 คำเตือนฮาร์ดแวร์ที่เอกสารเขียนไว้แล้ว แต่ยังไม่ได้ทำ

- **100nF ที่ VCC ของทุกจอ + 470µF ที่ราง 3.3V** — กันไฟตกตอน SPI กระชากพร้อมกัน (ยังไม่ได้ใส่)
- **R 22–33 Ω อนุกรมที่ SCLK** — กัน ringing (ยังไม่ได้ใส่ และจะยิ่งสำคัญขึ้นถ้าสัญญาณต้องผ่าน slip ring)
- **Polyfuse 1A ที่ขาเข้า 5V** (ยังไม่ได้ใส่)
- **MP1584 ต้องวัดให้ได้ 3.3V แล้วหยอดกาวล็อก trimpot** — โดนเขี่ยไป 5V = จอตายทั้งชุด
- **ห้ามจ่ายไฟสองทางพร้อมกัน** (USB + แหล่งจ่ายนอก)

### ข้อจำกัดจากเจ้าของงาน
- **บอร์ดต้องอยู่ที่ฐาน ไม่หมุนตามลูกบาศก์** เพราะบอร์ดต้องเชื่อมกับ digital twin / แผงข้อมูลบนเว็บ และต้องต่อปุ่มกดด้วย
- กำลังจะซื้อ slip ring **12 เส้น**
- งบทั้งโปรเจกต์ไม่เกิน 5,000 บาท มีของครบแล้วเป็นส่วนใหญ่
- **มีบอร์ดตัวเดียว ไม่เพิ่มบอร์ดที่สอง**

> ข้อแรกต่างจาก `cube-prototype.md` ที่วางให้บอร์ดอยู่บนถาดหมุน และให้ USB เป็นสายที่ข้ามรอยหมุนแทน
> ทั้งสองแบบทำให้บอร์ดคุยกับแผงเว็บได้ ต่างกันที่ว่า **อะไรข้ามรอยหมุน** — สัญญาณ SPI 8 เส้น หรือสาย USB 1 เส้น

### จำนวนเส้นที่ต้องใช้ ถ้าบอร์ดอยู่ฐาน

| สาย | จำนวน |
|---|---|
| GND | 2 (เผื่อทางกลับของสัญญาณ) |
| 3V3 VCC | 1 |
| SCK | 1 |
| MOSI | 1 |
| DC | 1 |
| RST | 1 |
| CS × 5 จอ | 5 |
| **รวม** | **12 พอดี ไม่เหลือเผื่อเลย** |

ถ้าเหลือ GND เส้นเดียวจะได้ 11 เส้น เหลือเผื่อ 1

### คำถามที่อยากให้ Codex ช่วยตอบ

1. **12 เส้นพอดีเป๊ะโดยไม่มีเส้นสำรอง เสี่ยงเกินไปไหม** ถ้าเส้นใดเส้นหนึ่งของ slip ring เสียหลังประกอบ จะไม่มีเส้นย้ายหนี
2. **ความต้านทานหน้าสัมผัสของ slip ring ราคาถูกแกว่งตามมุมหมุน** ตรงนี้เป็นปัญหากับ SCK/MOSI ที่ความเร็วเท่าไร และควรใส่ R อนุกรมที่ SCK ก่อนเข้า slip ring หรือหลังออก
3. **ลด CS จาก 5 เส้นเหลือ 3 เส้นด้วย 74HC138 บนฝั่งลูกบาศก์ คุ้มไหม** จะได้เส้นว่างคืน 2 เส้นไปทำ GND เพิ่มหรือเก็บเป็นสำรอง แลกกับต้องเพิ่ม IC และบัดกรีเพิ่มบนชิ้นที่หมุน
4. **ตัด RST ออกจาก slip ring ได้ไหม** โดยผูก RST ขึ้น 3V3 ผ่าน R ไว้บนลูกบาศก์แล้วใช้ SWRESET (0x01) ทางซอฟต์แวร์แทน ซึ่งเฟิร์มแวร์ยิงอยู่แล้วตาม B2 — จะได้เส้นคืน 1 เส้น
   ⚠️ **ความคิดนี้ขัดกับเอกสารของโปรเจกต์เอง** `cube-prototype.md` สั่งไว้ชัดว่าให้ต่อ RST ทุกใบเข้า GPIO เดียว **ไม่ใช่ RC**
   เหตุผลคือ "จอค้างระหว่างไล่บั๊กแล้วรีเซ็ตด้วยซอฟต์แวร์ไม่ได้ ต้องถอดปลั๊กทุกครั้ง" — ซึ่งบนชิ้นที่หมุนจะเจ็บกว่าเดิมมาก
   **ขอความเห็นว่าเหตุผลเดิมยังหนักกว่าการประหยัดสาย 1 เส้นหรือไม่**
5. **จำเป็นต้องมี slip ring จริงไหม** `cube-prototype.md` ที่ยังใช้อยู่วางไว้ว่าบอร์ดหมุนไปกับถาด
   มี**เฉพาะ USB/ไฟเข้า**ที่ข้ามรอยหมุน ผ่านช่องเดินสายที่ฐาน หมุนไป–กลับแบบมีขีดจำกัด มีตัวหยุดทางกล
   แบบนี้ **ไม่ต้องซื้ออะไรเพิ่มเลย ไม่มีหน้าสัมผัสเลื่อน และบอร์ดยังต่อ USB เข้าแผงเว็บได้ตามปกติ**
   สิ่งที่เสียไปคือหมุนต่อเนื่องไม่จำกัดรอบ
   **คำถาม: การหมุนไม่จำกัดรอบคุ้มกับการเอา SPI 8 เส้นไปฝากไว้กับหน้าสัมผัสเลื่อนหรือเปล่า**
   (`cube-review-5000-plan.md` ระบุด้วยว่า "360 องศา" ในงานนี้หมายถึงภาพพาโนรามา ไม่ใช่ข้อกำหนดว่ากลไกต้องหมุนต่อเนื่อง)
6. **ถ้ายืนยันว่าต้องหมุนต่อเนื่อง แต่ไม่เพิ่มบอร์ดที่สอง มีทางไหนบ้าง** ตัวเลือกที่นึกออกและข้อเสียที่รู้:
   - **บอร์ดอยู่ฐาน + SPI 8 เส้นผ่าน slip ring** → ตามที่กำลังจะซื้อ ข้อเสียคือสัญญาณความเร็วสูงผ่านหน้าสัมผัสเลื่อน
   - **บอร์ดอยู่บนถาดหมุน + ส่งข้อมูลขึ้นเว็บผ่าน WiFi + slip ring เหลือ 2 เส้น (ไฟ+GND)**
     ⚠️ `cube-prototype.md` สั่งให้ **ปิด WiFi/BT ในโค้ด** เพื่อประหยัด ~150 mA และลด jitter ซึ่งขัดกันโดยตรง
     และข้อ A7 บอกว่าไฟไม่พออยู่แล้ว ส่วนฝั่ง laptop ต้องเขียนใหม่จาก serial JSON เป็น websocket/UDP
     **ขอความเห็นว่าเหตุผล "ปิด WiFi" ยังหนักอยู่ไหม หรือปลดล็อกได้ถ้าจ่ายไฟจากหัวชาร์จผนัง**
   - **บอร์ดอยู่บนถาดหมุน + USB ผ่าน slip ring** → USB full-speed 12 Mbps เป็นสัญญาณ differential คู่
     **ทำได้จริงไหมบน slip ring ราคาถูก หรือควรตัดทิ้งไปเลย**
7. **มีเหตุผลอะไรที่ทำให้ไม่ควรส่ง SPI ผ่าน slip ring เลยหรือเปล่า** ถ้ามี ควรใช้วิธีไหนแทน

### หมายเหตุสำคัญสำหรับ Codex
ปัญหาจอที่เพิ่งเจอมาทั้งหมด **สาเหตุคือหน้าสัมผัส** (สายจัมเปอร์เสีย + เบรดบอร์ดไม่จับ)
slip ring **ก็คือหน้าสัมผัสที่ขยับตลอดเวลา** ความกังวลนี้จึงมีเหตุผลจากประสบการณ์ตรงของงานนี้เอง
ไม่ใช่จากทฤษฎีลอย ๆ — แต่ก็ยังไม่ใช่หลักฐานว่า slip ring จะมีปัญหา เพราะยังไม่ได้ซื้อและยังไม่ได้ลอง
