### การตรวจสถานะอุปกรณ์ฝั่ง Windows

เช็คซ้ำด้วย `Get-PnpDevice` ของ Windows ซึ่งเป็นคนละ API กับ `pyserial` ที่เครื่องมือใช้ ได้ผลคืออุปกรณ์ตัวเดิมสลับสถานะ `OK` ↔ `Unknown` ทุกไม่กี่วินาที ในช่วงที่ไม่มีใครเปิดพอร์ต
**ข้อสังเกต:** ต้องแยก "Windows รายงานอุปกรณ์ absent หรือเปลี่ยนสถานะ (PnP event/status change)" ออกจาก "การหลุดทางกายภาพ/ไฟฟ้าจริงของ USB" การที่สถานะเปลี่ยนเป็น `Unknown` เพียงอย่างเดียวไม่ได้รับรองว่าสายหรือฮาร์ดแวร์หลุดทางไฟฟ้าจริง (และไม่จำเป็นต้องสร้างระบบ Windows tracing ใหม่ในขั้นนี้)

## บั๊กที่เจอระหว่างทาง และแก้แล้ว: telemetry ถูกตัดกลางบรรทัดแบบเงียบ

รอบ B ครั้งแรกรายงานว่า **บอร์ดรีบูต 11 ครั้ง** ซึ่ง **ผิด** ตรวจข้อมูลดิบแล้วพบว่า
383 จาก 390 บรรทัดเป็น session เดียวกัน ส่วนอีก 5 บรรทัดคือ session เดิมที่**หายไปบางส่วนตรงกลาง**:

```
"session":"s3-af6e27ac-339-341dba4f"   383 บรรทัด  <- ของจริง
"session":"s3f"                          1 บรรทัด  <- ตัวเดิม แต่หายกลาง
"session":"s3-af6e27ac-339-341dba"       1 บรรทัด
"session":"s3-af6e27ac-339-341d"         1 บรรทัด
"session":"s3-af6e27ac-339-34"           1 บรรทัด
"session":"s3-af6e27ac-"                 1 บรรทัด
```

สาเหตุ: `Serial.setTxTimeoutMs(0)` **ไม่ได้แปลว่าไม่บล็อก แต่แปลว่าทิ้งไบต์ที่ไม่พอลง FIFO ทันที**
เมื่อไบต์ที่หายอยู่กลางสตริง สิ่งที่เหลือยัง **parse เป็น JSON ได้ปกติ** แต่ค่า session สั้นลง
ฝั่ง host จึงอ่านว่าเป็นบอร์ดคนละ boot ทั้งที่บอร์ดไม่ได้รีบูตเลยสักครั้ง

**ข้อมูลเสียที่ยัง parse ได้ อันตรายกว่าข้อมูลที่ parse ไม่ได้** เพราะมันให้คำตอบที่ผิดแบบดูน่าเชื่อ

แก้สองฝั่ง:

- **เฟิร์มแวร์** `sendLine()` ส่งข้อมูลพร้อม newline และเช็คจำนวนไบต์ที่เขียนได้จริง:
  - หากเขียนได้ไม่ครบและมีข้อมูลบางส่วนหลุดไป (`0 < written < wanted`) จะพยายามส่ง newline เพื่อกู้คืนขอบเขตบรรทัด ป้องกันไม่ให้ข้อความถัดไปถูกนำไปต่อท้ายสตริงที่ค้าง
  - หากเขียนไม่ได้เลย (`written == 0`) จะไม่ส่งข้อมูลเพิ่ม เพื่อรักษาจุดเริ่มต้นของบรรทัดถัดไป
  - พร้อมนับจำนวนไว้ในฟิลด์ `truncated_lines` ของทุก heartbeat และตั้ง tx timeout เป็น 20 ms (ทั้งนี้การพยายามคืนขอบเขตบรรทัดไม่ได้รับประกันว่าหลีกเลี่ยงข้อมูลเสียหายได้สมบูรณ์ทุกกรณีหาก FIFO เต็มสนิท)
- **เครื่องมือ** `_looks_truncated()` ใช้เป็น heuristic: ข้อความที่สงสัยจะถูกบันทึกเป็น `suspect_corrupt_line` พร้อมเก็บข้อความดิบ (raw) ไว้ และมีเงื่อนไขตรวจสอบว่าหาก uptime เริ่มต้นใหม่จากศูนย์จริง จะต้องนับเป็นการรีบูตจริงโดยไม่ถูก heuristic บดบัง

**ผลหลังแก้:** รอบ B ครั้งที่สอง 741 บรรทัด — `<truncated` 0 ครั้ง, `truncated_lines` เป็น 0 ตลอด, session เดียว

## สิ่งที่แก้ ตามข้อ 1–3

### ข้อ 1 — ให้มีผู้ใช้พอร์ตเพียงตัวเดียว และเปิดค้างไว้

**เส้นทางที่เปิดพอร์ตจริง ตรวจแล้วมีเท่านี้** (ไม่ได้ฆ่า process ใด):

| ที่ | ทำอะไร |
| --- | --- |
| `laptop/core.py` `SerialWorker._open()` | ตัวเดียวที่ dashboard ใช้ |
| `laptop/app.py:251` | `list_ports.comports()` แค่ลิสต์รายชื่อ ไม่เปิดพอร์ต |
| `tools/usb_watch.py` | เครื่องมือตรวจตัวใหม่ |
| PlatformIO Monitor | ใช้ค่าจาก `platformio.ini` |

ตอนตรวจไม่มี process อื่นถือพอร์ตอยู่ (ไม่พบ python/putty/arduino/pio ที่รันค้าง)

**แก้ใน `laptop/core.py`:**

- **เธรดเดียวเป็นเจ้าของพอร์ต** เดิม `send()` เขียนลงพอร์ตจากเธรดผู้เรียก ขณะที่ `_pump()` ก็เขียนจากเธรด worker
  สองเธรดเขียน handle เดียวกันสลับกันได้กลางบรรทัด JSON ตอนนี้ `send()` เข้าคิวอย่างเดียว มีแต่ worker ที่เขียน
- **ลดโอกาส UI ค้างจากการเขียนพอร์ต** ออกแบบให้แยกเธรด โดย `send()` ทำงานผ่าน outbox queue เธรด UI จึงไม่บล็อกกับการเขียนพอร์ตโดยตรง แม้ไม่ได้เป็นคำรับประกันทุกเส้นทางทำงานของแอป
- **ใส่ `write_timeout`** เดิมไม่ได้ตั้ง การเขียนที่ระบายไม่ออกจึงรอได้ไม่จำกัด
- **`stop()` รอและตรวจสอบการปล่อย handle** ออกแบบให้ `join()` ตาม timeout ที่กำหนด และส่งสถานะกลับว่าเธรดยุติจริงหรือไม่ เพื่อลดโอกาสแย่งพอร์ตกับ esptool แต่หากเธรดยังไม่หยุดตาม timeout จะมีข้อความเตือนว่าพอร์ตอาจยังถูกถืออยู่
- **reconnect เฉพาะเมื่อมีหลักฐาน** อ่านแล้วไม่ได้ข้อมูลถือเป็นเรื่องปกติ ไม่ log และไม่ reconnect
  ส่วน JSON ที่ parse ไม่ผ่านถือเป็นข้อมูลเสีย ไม่ใช่ลิงก์ตาย จึงอ่านต่อ
- **บันทึกเหตุการณ์พร้อมเหตุผลและเวลา** `SerialLinkLog` เขียน `open_attempt`, `open_success`, `open_error`,
  `close`, `read_error`, `write_error`, `reconnect` เป็น JSON lines ลง `output/usb-stability/`
  และส่งเข้า console ของ dashboard ด้วย เดิมเหตุผลการหลุดถูก hardcode เป็นข้อความเดียวทุกกรณี

`protocol`, `ACK`, `session` และ `EventDeduper` ไม่ถูกแตะ

### ข้อ 3 — DTR/RTS

- `platformio.ini` เพิ่ม **`monitor_dtr = 1`, `monitor_rts = 0`** ทั้งสอง environment ให้ตรงกับ dashboard
  ตรวจแล้วว่า PlatformIO 6.2.0 ที่ติดตั้งอยู่รองรับสองออปชันนี้จริง (อยู่ใน `ProjectOptions`)
- ค่าเหล่านี้มีผลกับ monitor เท่านั้น **ไม่แตะ reset sequence ที่ esptool ใช้ตอน upload** และไม่แตะ download mode
- ตรวจแล้วว่าไม่มีการเปลี่ยน DTR/RTS หลัง `open()` ที่ใดเลย ทั้งตอนเชื่อมต่อและตอน reconnect
  ทุกครั้งตั้งค่าก่อน `open()` แล้วไม่แตะอีก
- **แก้คำอธิบายที่ผิด** docstring เดิมของ `_open()` เขียนว่า "เปิดพอร์ตโดยไม่แตะ modem line" และอ้างว่า
  pyserial ยก DTR/RTS ทำให้บอร์ดรีบูตทุกครั้งที่ต่อ ซึ่งขัดกับโค้ดของตัวเองที่ตั้ง `dtr=True`
  ตอนนี้เขียนตามที่วัดได้ พร้อมระบุว่าเป็นผลจากเครื่องนี้ ไม่ใช่คำรับประกันข้าม OS/driver
  เพราะ pyserial เองระบุว่าบาง driver ยังกระตุก control line ตอนเปิดพอร์ต
- **แก้เอกสารเก่าที่ยังอ้างข้อผิด** `output/luna-04-status.md` ข้อ 2 เคยเขียนว่าต้องกด DTR/RTS ลงก่อนเปิด
  ใส่หมายเหตุยกเลิกไว้แล้ว พร้อมเหตุผลว่า `dtr=False` ทำให้บอร์ดเงียบสนิท
- **เทสที่ยืนยันข้ออ้างเก่า** `test_opening_the_port_does_not_raise_the_modem_lines` บังคับให้เป็น `(False, False)`
  และ **fail อยู่ก่อนเริ่มงานนี้แล้ว** เปลี่ยนเป็นยืนยันค่าที่วัดได้จริงคือ `(True, False)`

## รอบ C — ทำได้บางส่วน

ส่วนที่ต้องมีคนนั่งกดปุ่มและดูว่า UI ค้างไหม **ยังไม่ได้ทำ** ต้องให้ผู้ใช้เป็นคนทำ

ส่วนที่วัดได้โดยไม่ต้องมีคน คือเส้นทาง `SerialWorker` จริงที่ dashboard ใช้ รันผ่าน `tools/usb_soak.py`
ถือ connection เดียว 10 นาที และส่ง `get_state` ทุก 30 วินาทีแบบเดียวกับปุ่ม Request state
เพื่อพิสูจน์ว่าคำสั่งไม่ทำให้เปิดพอร์ตใหม่

**ผล — ผ่าน:** 600 วินาที · **เปิดพอร์ต 1 ครั้ง · reconnect 0 · disconnect 0**
ส่งคำสั่ง 19 ครั้งโดยไม่เปิดพอร์ตใหม่เลย · รับ 3,076 ข้อความ (state 2,458 · heartbeat 599 · hello 19)
· **session เดียว** · **uptime เดินไป 599,917 ms ขณะเวลาจริงผ่านไป 599,903 ms** ต่างกัน 14 ms

## การตรวจอัตโนมัติ

| อะไร | ผล |
| --- | --- |
| `python -m unittest discover -s tests -t tests` | **100 tests, 1 failure** |
| Build `esp32-s3-zero` | SUCCESS · RAM 6.0% · Flash 24.5% |
| Build `diag` | SUCCESS |

เทสที่ fail คือ `test_only_enabled_faces_are_initialized` ซึ่งนับ `new Adafruit_ST7789` ได้ 2 แทนที่จะเป็น 1
**fail อยู่ก่อนเริ่มงานนี้แล้ว** เป็นเรื่องของโหมดจอเดี่ยวที่ยังเหลืออยู่ในโค้ด ไม่เกี่ยวกับ USB
ใบสั่งงานระบุว่าไม่ให้แก้ระบบจอเพื่อแก้ปัญหา USB จึงไม่แตะ

เทสที่เพิ่ม 6 ตัว ทดสอบเฉพาะพฤติกรรมที่แก้: เปิดพอร์ตด้วย DTR สูง, มี write timeout,
`send()` ไม่เขียนจากเธรดผู้เรียก, write ที่ล้มเหลวถูกบันทึกและรายงานเป็น link failure,
`stop()` รอจนปล่อยพอร์ต, และ heartbeat ไม่ทำให้ dashboard พัง

## ข้อจำกัดที่ยังค้าง

1. **ยังไม่รู้ว่าทำไมถึงหลุดช่วงหลังแฟลช** รู้แค่ว่ามันเกิดจริง วัดได้ ไม่ใช่ความผิดของ dashboard และหายไปเอง
2. **ยังแยกไม่ได้ว่าอะไรทำให้หยุดหลุด** เวลาที่ผ่านไป หรือการมีโปรแกรมเปิดพอร์ตค้างไว้
3. **`reset_reason` เป็น `0` (unknown)** ไม่ใช่ `poweron` ตามที่คาด บันทึกไว้เป็นข้อสังเกต ยังไม่ตีความ
4. **รอบ C ส่วน UI ยังไม่ได้ทดสอบ** ต้องมีคนกดปุ่มและดูว่าค้างไหม
5. **ทดสอบโดยไม่มีจอต่ออยู่เลย** โหลดไฟและสัญญาณของจริงต่างจากนี้ ผลนี้ใช้อ้างกับกรณีต่อจอครบไม่ได้

### การทดลองถัดไป หนึ่งข้อ

แฟลชแล้วรัน presence-only 10 นาทีทันที **โดยไม่เปิดพอร์ตเลยสักครั้ง**

```bash
python tools/usb_watch.py --port COM6 --presence-only --seconds 600
```

ถ้าอาการหยุดเองโดยไม่มีใครเปิดพอร์ต แสดงว่าหยุดได้เองในหน้าต่างนั้นโดยไม่ต้องมีแอปเปิดพอร์ต แต่ยังสรุปไม่ได้ว่าเวลาคือปัจจัยเดียว
ถ้ายังพบเหตุการณ์หลุดครบ 10 นาที บอกได้เพียงว่าอาการยังไม่หยุดภายในหน้าต่างที่สังเกต ต้องอาศัยการทดลองเปิดพอร์ตตามหลังเพื่อดูผล และถึงอย่างนั้นยังไม่ใช่ข้อพิสูจน์เชิงเหตุผลเด็ดขาดจากการทดลองครั้งเดียว

## วิธีใช้งาน

**ใช้งานปกติ**

1. เปิด dashboard `python laptop/app.py`
2. Settings เลือก **COM6** แล้วกด **Connect**
3. เปิดค้างไว้ ไม่ต้องกด Disconnect/Connect ซ้ำ คำสั่งทุกอันใช้ connection เดิม

**ก่อนแฟลชโค้ดใหม่**

1. กด **Disconnect** ในหน้า Settings ก่อน ปุ่มนี้รอจนพอร์ตถูกปล่อยจริงแล้วจึงคืนค่า
2. แฟลช
3. **หลังแฟลช ถ้าได้ยินเสียงติ๊ด ๆ ไม่ต้องตกใจ** วัดแล้วว่าเป็นช่วงชั่วคราวและบอร์ดไม่ได้รีเซ็ตตัวเอง
   กด Connect แล้วเปิดค้างไว้ หรือรอสักครู่ให้ลิงก์นิ่ง

**เก็บหลักฐานเมื่อสงสัยว่าหลุด**

```bash
python tools/usb_watch.py --port COM6 --seconds 300
```

ไฟล์เหตุการณ์และบรรทัดดิบจะอยู่ใน `output/usb-stability/` พร้อมเวลาและเหตุผลของทุกเหตุการณ์

### 2. การแก้โค้ด

- `firmware/src/main.cpp` (`sendLine`): ปรับให้ส่ง payload พร้อม `\n` รวดเดียว และมี `gLineIncomplete` จดจำสถานะบรรทัดค้าง หากเกิดการส่งไม่ครบและกู้คืน newline ไม่สำเร็จ จะปฏิเสธการส่ง payload ใหม่เพื่อป้องกันการต่อข้อความกลางสาย โดยมี timeout จำกัด (ไม่รอไม่สิ้นสุด)
- `tools/usb_watch.py` (`watch_link`): ปรับ `_looks_truncated` ให้เป็น heuristic โดยบันทึกเป็น `suspect_corrupt_line` พร้อมเก็บ raw text และเพิ่มเงื่อนไขตรวจ `uptime_ms` เริ่มใหม่จากศูนย์เพื่อไม่ให้ heuristic กลบการรีบูตจริง
- `laptop/core.py` (`SerialWorker`, `DashboardModel`): `stop()` คืนค่าบูลีนระบุว่าเธรดยุติและปล่อยพอร์ตจริงหรือไม่; `send()` ปฏิเสธการเข้าคิวหลังสั่งหยุด; `_drain_outbox()` หยุดลูปทันทีเมื่อ `stop_requested` ถูกตั้ง; เพิ่ม `stopping()` ในโมเดล
- `laptop/app.py` (`disconnect`, `connect`): หาก `stop()` คืนค่า `False` จะรักษา reference ของ worker เดิมไว้และแสดงสถานะ `stopping`; ฟังก์ชัน `connect()` จะปฏิเสธการสร้าง worker ใหม่จนกว่า worker ตัวเดิมจะสิ้นสุดการทำงานจริง
- `tests/test_dashboard_core.py`: เพิ่ม tests ครอบคลุมการจำสถานะ incomplete line ใน `sendLine`, การรักษา worker reference และบล็อก connect เมื่อ stop ล้มเหลว

### 4. สิ่งที่ยังไม่รับรอง

### 5. ขั้นตอนถัดไปหนึ่งข้อ

นำบอร์ดต่อสายจอและทดสอบการแสดงผลและควบคุมมุมมอง 270 องศาในโหมดปกติของต้นแบบต่อไป (หากต้องการตรวจ GUI ให้รันตามเช็กลิสต์ 6 ข้อด้านล่าง)

#### รายการทดสอบ GUI Dashboard สำหรับผู้ใช้ (ไม่เกิน 6 ข้อ)
1. รัน `python laptop/app.py` เปิดหน้าต่าง Dashboard
2. ไปที่แท็บ Settings เลือกพอร์ต COM ที่พบจริง (เช่น `COM6`) แล้วกดปุ่ม **Connect**
3. คลิกบนพื้นที่ว่างของหน้าปัดเพื่อโฟกัสหน้าต่าง แล้วทดสอบกดปุ่มทิศทาง **Up / Down** (เปลี่ยนระดับความลึก) และ **Left / Right** (เปลี่ยนมุม Yaw)
4. ทดสอบกดปุ่มตัวเลข **1 (Scan)**, **2 (Collect)** และ **3 (Analyze)** สังเกตการตอบสนองบนแถบสถานะ/คอนโซล
5. กดปุ่ม **Request state** เพื่อตรวจว่าคำสั่งยังใช้ connection เดิมโดยไม่หลุดหรือเปิดพอร์ตใหม่
6. กดปุ่ม **Disconnect** ตรวจสอบว่าพอร์ตถูกปล่อยโดยสมบูรณ์และโปรแกรมไม่ค้าง
