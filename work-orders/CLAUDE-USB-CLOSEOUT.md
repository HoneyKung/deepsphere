# ใบสั่งงาน Claude: ปิดงาน USB แบบจำกัดรอบ แล้วส่งต่องานต้นแบบ 270 องศา

## เป้าหมายและขอบเขต

ตรวจจุดค้างจาก `output/claude-usb-stability-status.md` ให้มีข้อสรุปที่ใช้ทำงานต่อได้ ไม่ต้องพิสูจน์ต้นเหตุ USB ทุกชั้น งานหลักของผู้ใช้ขณะนี้คือบอร์ดเดียว แสดงผลจอ หมุนมือ 270 องศา และใช้งาน Scan → Collect → Analyze กับโน้ตบุ๊ก สลิปริงและสองบอร์ดยังเป็นแผนภายหลัง

ทำเฉพาะ workspace `C:\Users\Acer\Downloads\oceanX\prototype-v1` ใบนี้เป็นงานต่อจากผลเดิม ไม่ให้เริ่ม USB investigation ใหม่ทั้งหมด ไม่แก้ภาพทะเล พิกัด SPI ผังสายจอ หรือเพิ่มฟีเจอร์ ไม่มีอีโมจิในโค้ด

ใบนี้ร่างไว้ส่งต่อ ยังไม่ใช่หลักฐานว่าได้ทดลองหรือแฟลชแล้ว เมื่อผู้ใช้มอบหมายให้ดำเนินการ ให้ใช้ขอบเขตและจุดหยุดต่อไปนี้

## ผลเดิมที่ใช้ต่อได้ ไม่ต้องรันซ้ำ

- การทดสอบเดิม **ไม่มีจอต่ออยู่** ใช้ยืนยันได้เฉพาะเงื่อนไขนั้น
- SerialWorker เปิดค้าง 600 วินาที: open 1, reconnect/disconnect 0, session เดียว; uptime เพิ่ม 599,917 ms เทียบเวลาจริง 599,903 ms
- รอบ B และ D เดิมมีหลักฐานต่อเนื่องแล้ว ไม่ต้องทำ soak ของ SerialWorker หรือ open/close สามรอบซ้ำ
- DTR=True, RTS=False เป็น baseline ที่ใช้ได้กับเครื่องนี้แล้ว ไม่ทดลองสลับค่าใหม่โดยไม่มีหลักฐานใหม่
- Build ทั้งสอง environment เคยผ่าน; 100 tests มี failure เดิมหนึ่งตัวเกี่ยวกับจอ ไม่แก้หรือเปลี่ยน expected เพื่อให้รายงานเขียว
- รอบ C ยังไม่ได้ทดสอบ GUI จริง ส่วนเหตุการณ์หลังแฟลชยังไม่แยกผลของเวลาออกจากการเปิดพอร์ต

## งบการทำงานเพื่อไม่ให้วนและใช้โทเคนเกินจำเป็น

- อ่านรายงานข้างต้นหนึ่งครั้ง จากนั้นใช้ `rg` และอ่านเฉพาะฟังก์ชันเกี่ยวข้อง ไม่อ่านทั้ง repository หรือ raw log ทั้งหมดเข้า context
- รวมคำสั่งอ่านที่เป็นอิสระไว้ใน tool call เดียว เก็บผลยาวลงไฟล์ แล้วแสดงเพียงสรุปจำนวนกับตัวอย่างผิดปกติไม่เกิน 3 รายการ
- ไม่เปิด agent เพิ่ม ไม่ติดตั้งเครื่องมือ/ไดรเวอร์ ไม่เปลี่ยน Python, SDK, USB mode, upload speed หรือ esptool flags
- ทดสอบหลังแฟลชได้ **หนึ่งชุด**; GUI ได้ **หนึ่งชุด** ไม่วนทำ A/B/C/D ใหม่ทั้งหมด
- ใช้การแก้หนึ่งชุด แล้วรัน tests ที่เกี่ยวข้องหนึ่งรอบ อนุญาตรอบแก้ซ้ำอีกหนึ่งรอบเฉพาะความผิดที่การแก้ของตนทำให้เกิด หากยังไม่ผ่าน ส่งหลักฐานและหยุด
- Build เฉพาะ environment ที่ source/config เปลี่ยน ถ้าแก้เฉพาะ Python/รายงาน ไม่ build firmware; ไม่ buildfs เพราะ assets ไม่อยู่ในขอบเขต
- ไม่รัน native geometry vectors หรือ image previews เพราะไม่เกี่ยวกับ USB
- งาน hardware ต้องไม่แย่งพอร์ตจากผู้ใช้หรือโปรแกรมอื่น หากไม่พร้อม ทำงานเตรียมและรายงาน `NOT RUN` แล้วจบ ไม่เปิดเครื่องมือรอผู้ใช้วน ๆ
- เครื่องมือเก็บข้อมูลต้องมี timeout และคืน handle เมื่อจบ รอผลคำสั่งเป็นช่วงไม่เกิน 60 วินาที สรุปความคืบหน้าสั้น ๆ ระหว่างการทดสอบ โดยไม่เปิด serial เพิ่ม
- จบแล้วรายงานทันที ไม่เสนอว่าจะทดลองต่อเอง ไม่แฟลชซ้ำเพื่อความสบายใจ

## งาน 1: แก้ข้อสรุปในรายงานให้ตรงหลักฐาน

แก้ในรายงานเดิม ไม่สร้างรายงานประวัติซ้ำอีกฉบับ และไม่แก้ raw logs:

1. เปลี่ยน “dashboard ไม่ใช่สาเหตุ” เป็น “พบเหตุการณ์อุปกรณ์หาย/กลับมาแม้ dashboard ไม่ทำงาน จึงไม่อธิบายได้ด้วย dashboard อย่างเดียว” ไม่ตัดปัจจัยร่วมทั้งหมด
2. เปลี่ยน “บอร์ดไม่ได้รีเซ็ตตัวเอง” ให้ระบุหน้าต่าง B/C-soak/D ที่มี session และ uptime รองรับ ไม่ขยายไปครอบคลุมช่วง presence-only ที่ไม่มี uptime
3. เปลี่ยน “เกิดเฉพาะหลังแฟลชแล้วหายเอง” เป็นข้อสังเกตจากสามรอบ พร้อมระบุว่ามีการเปิดพอร์ตคั่นอยู่ จึงยังยืนยันสาเหตุไม่ได้
4. ยกเลิกข้อความ “ถ้ายังหลุดครบ 10 นาที แปลว่าการเปิดพอร์ตทำให้นิ่ง” ผลแบบนั้นบอกได้เพียงว่ายังไม่หยุดภายในหน้าต่างที่รอ ต้องมีการทดลองเปิดพอร์ตตามหลัง และถึงอย่างนั้นยังไม่ใช่ข้อพิสูจน์เชิงเหตุผลเด็ดขาดจากการทดลองครั้งเดียว
5. แยก “Windows รายงานอุปกรณ์ absent/status เปลี่ยน” ออกจาก “USB หลุดทางไฟฟ้าจริง” ตรวจว่าใช้ present-device query หรือรวม device เก่าด้วย; `Unknown` อย่างเดียวไม่พอรับรองการถอดต่อทางไฟฟ้า ไม่จำเป็นต้องสร้างระบบ Windows tracing ใหม่
6. เปลี่ยน “UI ค้างไม่ได้อีก” และ “Disconnect คืน handle แน่นอน” เป็นพฤติกรรมที่ออกแบบไว้และผลที่ตรวจได้จริง การมี timeout/join ไม่ใช่คำรับประกันทุกเส้นทาง
7. เก็บ `reset_reason=0/unknown` ตามเดิม ไม่ไล่หาสาเหตุของค่านี้ในรอบนี้

## งาน 2: ตรวจความน่าเชื่อถือของข้อมูลและจุดหยุดโปรแกรมเฉพาะที่จำเป็น

อ่านเฉพาะ `main.cpp:sendLine()`, `SerialWorker` ใน `laptop/core.py`, จุด Connect/Disconnect ใน `laptop/app.py` และการนับ boot ใน `tools/usb_watch.py`

### 2.1 บรรทัดถูกตัด

ข้อสังเกตจาก Astra: `sendLine()` ตรวจจำนวนไบต์ของ payload แล้วเติม `<truncated` และ newline ด้วยคำสั่งที่ไม่ได้ตรวจจำนวนไบต์ การส่ง marker เองจึงยังอาจไม่ครบเมื่อ FIFO เต็ม อย่ารายงานว่ากลไกนี้รับประกันว่า JSON เสียทุกครั้ง

- ตรวจ implementation `HWCDC::write` ของ framework ที่ติดตั้งจริงเฉพาะส่วนการคืนค่า/timeout หากจำเป็นต่อการตัดสินใจ ไม่ดึง SDK ใหม่
- ถ้าแก้ได้เล็กน้อย ให้รักษาลำดับ byte stream: ไม่เอาข้อความใหม่ไปต่อท้ายข้อความที่ส่งค้าง; การส่งค้างต้องจบอย่างถูกต้องหรือถูกทิ้งพร้อมการคืนขอบเขตบรรทัดที่เชื่อถือได้ โดยไม่รอ host ไม่สิ้นสุด
- ถ้าต้องรื้อ transport เพื่อรับประกันทั้งหมด ให้บันทึกข้อจำกัดและจบส่วนนี้ ไม่สร้าง protocol ใหม่หลายชั้นเพื่อปิดทฤษฎีทุกกรณี
- `_looks_truncated()` เป็นเพียง heuristic: ข้อความที่สงสัยควรนับ `suspect/corrupt` และเก็บ raw ไว้ ไม่ให้ความคล้ายของ session กลบ boot ใหม่ที่มี uptime เริ่มใหม่จริง
- หากแก้โค้ดส่วนนี้ ทดสอบจำลองอย่างน้อยกรณี full write, short/zero write ต่อเนื่อง แล้วกลับมาส่งได้ และข้อความ boot ใหม่จริง ต้องไม่รอไม่สิ้นสุดหรือรายงาน corrupt เป็น boot ที่ยืนยันแล้ว

### 2.2 การหยุด worker

- ตรวจ `stop()` กับ `join(timeout)` ว่ามีการเช็กว่าเธรดจบจริงหรือไม่ หากยังไม่จบ UI ต้องไม่บอกว่าพอร์ตพร้อม upload แล้ว
- ตรวจว่าการ drain คิวไม่ทำให้หยุด worker ไม่ได้เมื่อมีคำสั่งเข้าต่อเนื่อง แก้เฉพาะถ้าเห็นเส้นทางผิดจริง
- ห้ามใช้การ kill process หรือบังคับ reset บอร์ดแทนการจัดการ connection

ส่วนนี้เป็นการตรวจแก้เฉพาะข้ออ้างที่มีผลต่อการตรวจรับ ไม่ใช่งาน refactor SerialWorker ทั้งตัว

## งาน 3: ตรวจ GUI จริงหนึ่งรอบ — สิ่งสำคัญต่อการเดินหน้าต้นแบบ

ใช้ dashboard จริง ไม่ใช้ `usb_soak.py` แทน GUI บอร์ดใช้ firmware เดิมได้ถ้าไม่มีการแก้ firmware จากงาน 2

- ปิด logger/monitor ก่อน ให้ dashboard ถือ COM เพียงตัวเดียว ใช้ชื่อพอร์ตที่พบจริง ไม่ถือว่า COM6 ยังถูกเสมอ
- เปิดครั้งเดียวรวมประมาณ 5 นาที ในช่วงนั้นให้ผู้ใช้ทดลอง Up/Down, Left/Right, 1 Scan, 2 Collect, 3 Analyze รวมทั้ง Request state และ Disconnect ตอนท้าย
- คีย์บอร์ดต้องโฟกัสหน้าต่าง dashboard ไม่ใช่ช่องพิมพ์ข้อความ ปุ่มควรส่งคำสั่งไปบอร์ดจริงและมีผลตอบกลับ ไม่เอา simulator มาแทน
- เก็บว่ากดอะไร ได้ response/ACK อะไร และ UI ยังรับการลากหน้าต่าง/กดปุ่มได้หรือไม่ หากทำครบลำดับ Scan → Collect → Analyze ไม่ได้เพราะไม่มีจอหรือไม่เข้าเงื่อนไขเกม ให้รายงานข้อจำกัดนั้น ไม่อ้างว่า game loop ผ่าน
- ถ้าไม่มีจอต่ออยู่ ยังทดสอบความตอบสนองของ GUI/serial ได้ แต่ต้องเขียนว่าไม่ตรวจภาพบนจอและโหลดไฟจริง
- หลัง Disconnect ต้องตรวจว่า worker สิ้นสุดและ handle ถูกปิดจริง ไม่ต้องแฟลชเพื่อพิสูจน์ว่าปิดพอร์ตแล้ว
- ถ้าผู้ใช้ไม่พร้อมทดสอบ ให้เตรียมรายการกดไม่เกิน 6 ข้อ ส่งว่า `GUI: NOT RUN` แล้วจบ ห้ามรอเฝ้าหรือทำ simulation เพิ่มเพื่อให้เหมือนเสร็จ

เกณฑ์ผ่านเฉพาะ GUI/USB: UI รับการใช้งานได้, คำสั่งใช้ connection เดิม, ไม่มี exception ทำโปรแกรมล่ม, และ Disconnect ปล่อย connection ตามที่ตรวจได้จริง

## งาน 4: ทดลองหลังแฟลชหนึ่งชุด เฉพาะเมื่อฮาร์ดแวร์พร้อม

ใช้เพื่อปรับวิธีเริ่มใช้งาน ไม่เป็นเงื่อนไขว่าต้องรู้ต้นเหตุเด็ดขาดก่อนกลับไปทำจอ หากผู้ใช้ยังสั่งหยุดงานกับบอร์ดอยู่ ให้คง `NOT RUN` ไม่เริ่มแฟลช

เงื่อนไข: คงแบบเดิมของรายงาน คือ USB อย่างเดียวและไม่มีจอ ผู้ใช้เป็นผู้จัดสายและแจ้งความพร้อม; อย่าสั่งรื้อสายที่กำลังทำเพื่อการทดลองนี้ ถ้าสภาพต่างออกไปให้บันทึกและไม่เรียกว่าเทียบตรงกับผลเก่า

1. หากจะทำชุดนี้ ให้แฟลช binary ที่ต้องการตรวจ **ครั้งเดียว** ตรวจพอร์ตและปล่อยผู้ถือพอร์ตอื่นก่อน ใช้ค่าที่แฟลชผ่านเดิม ปิด auto-monitor และบันทึกเวลาเริ่ม/จบ upload
2. ทันทีหลัง upload เริ่ม `presence-only` 600 วินาที ห้ามเปิด COM ระหว่างหน้าต่างนี้ การเปิดของ esptool ระหว่าง upload เป็นส่วนของจุดตั้งต้น ไม่แอบนับว่าไม่เคยเปิดมาก่อนเลย
3. ถ้าอาการหายเองก่อนครบ ให้รอจนจบหน้าต่างเดียวและรายงาน “หยุดในหน้าต่างนี้โดยไม่มีแอปเปิด COM หลัง upload” ห้ามสรุปว่าเวลาคือสาเหตุเดียว
4. ถ้ายังมีเหตุการณ์หาย/กลับมาช่วงท้าย ให้หยุด presence-only แล้วเปิด logger หนึ่งครั้ง ค้างอีกไม่เกิน 180 วินาที ปิด auto-reconnect เพื่อไม่ทำให้การทดลองกลายเป็นเปิดพอร์ตหลายรอบ
5. ถ้าเปิดไม่ได้หรือหลุด ให้บันทึกความล้มเหลวแล้วจบ ไม่ retry/แฟลชซ้ำ ถ้าเปิดแล้วนิ่ง ให้รายงาน “สอดคล้องกับสมมติฐานว่าการเปิดค้างช่วยในรอบนี้” ไม่รับรองสาเหตุจากครั้งเดียว

ใช้เครื่องมือเดิมที่รองรับตัวเลือกแล้ว:

```powershell
# ทำจากโฟลเดอร์ prototype-v1; แทน PORT_ACTUAL ด้วยพอร์ตที่ยืนยันแล้ว
& '.\.venv-validation\Scripts\python.exe' tools/usb_watch.py --port PORT_ACTUAL --presence-only --seconds 600
# ใช้เฉพาะเมื่อเข้าเงื่อนไขข้อ 4 หลังคำสั่งแรกจบแล้ว
& '.\.venv-validation\Scripts\python.exe' tools/usb_watch.py --port PORT_ACTUAL --seconds 180 --no-reconnect
```

ห้ามแก้ driver, power management, registry, สาย USB หรือแหล่งจ่ายระหว่างชุดนี้ ห้ามรัน logger และ dashboard พร้อมกัน

เพดานงาน 4: upload หนึ่งครั้ง + สังเกต 10 นาที + เปิด logger ตามเงื่อนไขไม่เกิน 3 นาที ผลยังไม่ชัดให้ `INCONCLUSIVE` แล้วจบ ไม่ตั้งชุดทดลองใหม่เอง

## ส่งมอบและจุดจบ

เพิ่มหัวข้อท้ายรายงานเดิมชื่อ “Closeout” สั้นไม่เกินประมาณหนึ่งหน้า ระบุ:

| รายการ | ต้องมี |
| --- | --- |
| ข้อสรุปที่แก้ | อ้างประโยคเดิมแบบสั้นและข้อความใหม่ |
| การแก้โค้ด | ไฟล์/ฟังก์ชัน เหตุผล หรือระบุว่าไม่จำเป็นต้องแก้ |
| Validation | tests/build ที่รันจริง รวม failure เดิมตามจริง |
| GUI | PASS / FAIL / NOT RUN พร้อมเงื่อนไขว่าต่อจอหรือไม่ |
| หลังแฟลช | ผลชุดเดียว / INCONCLUSIVE / NOT RUN |
| สิ่งที่ยังไม่รับรอง | โหลดจอจริง, ภาพบนจอ, รากเหตุ USB ตามที่ยังค้าง |
| ขั้นต่อไป | หนึ่งขั้นที่นำกลับไปทดสอบจอและต้นแบบ 270 องศา |

หลักฐานใหม่ใช้ชื่อ run ไม่ซ้ำใน `output/usb-stability/` เก็บ raw ไว้บนดิสก์ ไม่คัดลงรายงานทั้งหมด

ข้อความส่งผู้ใช้ตอนจบไม่เกิน 8 บรรทัด: ทำอะไรเสร็จ, ผลที่พิสูจน์ได้, ส่วน NOT RUN/ยังไม่รู้, ลิงก์รายงาน และขั้นต่อไปหนึ่งข้อ ห้ามเขียน “เสร็จครบทั้งหมด” หาก GUI ยัง NOT RUN หรือยังมีส่วนที่ไม่ได้ทำ

หยุดหลังส่งมอบตามนี้ ไม่กลับไปทำ soak, flash, build หรือค้นหาสาเหตุเพิ่มโดยไม่มีงานใหม่จากผู้ใช้
