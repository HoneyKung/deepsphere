# ใบสั่งงาน Claude Code: ตรวจและแก้ USB หลุด ข้อ 1–3

## เป้าหมาย

ทำให้ ESP32-S3-Zero สื่อสารกับ dashboard ผ่าน USB ได้ต่อเนื่อง และแยกให้ได้ด้วยหลักฐานว่าอาการเกิดจากบอร์ดรีเซ็ต, USB หลุดโดยบอร์ดยังรัน, หรือโปรแกรมฝั่งคอมเปิด/ปิดพอร์ต เป้าหมายใกล้ที่สุดคือโปรโตไทป์ใช้งานได้วันศุกร์

ทำงานใน `C:\Users\Acer\Downloads\oceanX\prototype-v1` เท่านั้น อ่านสถานะจริงก่อนแก้ เพราะอาจมีการแก้ต่อหลังร่างใบนี้ ไม่ใช้เดโมเก่า ไม่เปลี่ยนภาพทะเล ระบบจอ พิกัด หรือปุ่มควบคุมเพื่อแก้ปัญหา USB และไม่ใส่อีโมจิในโค้ด

ใบนี้เป็นงานตรวจและแก้ข้อ 1–3 ไม่รวมซื้ออุปกรณ์ เปลี่ยนบอร์ด ย้ายไป UART หรือเพิ่มกล้อง/มอเตอร์ การร่างใบนี้ไม่ได้สั่งให้เริ่มแฟลชทันที ระหว่างเตรียมงานให้ตรวจและ build ได้ ส่วนการทดสอบกับบอร์ดให้ทำในช่วงที่ผู้ใช้พร้อมและไม่มีโปรแกรมอื่นถือพอร์ตอยู่

## สิ่งที่พบตอนร่างใบสั่งงาน

- `platformio.ini` มี environment `esp32-s3-zero` และ `diag` ทั้งคู่ตั้ง `ARDUINO_USB_CDC_ON_BOOT=1` และ `ARDUINO_USB_MODE=1` แต่ยังไม่มีค่า `monitor_dtr`/`monitor_rts` ระบุไว้
- `laptop/core.py` ใน `SerialWorker._open()` สร้าง Serial แบบยังไม่เปิด ตั้ง `dtr=True`, `rts=False` แล้วจึง `open()` อยู่แล้ว มี reconnect delay 1 วินาที
- `firmware/src/main.cpp` มี reset reason ในข้อความเริ่มต้นและมี session ID อยู่แล้ว ให้ใช้ของเดิมถ้าเพียงพอ
- `firmware/src/diag/panel_check.cpp` มี `esp_reset_reason()` และตัวนับรอบอยู่แล้ว แต่ไม่ควรถือว่าข้อความตอนเริ่มต้นจะถูกคอมรับทันเสมอ
- ยังไม่ได้ยืนยันว่า binary บนบอร์ดตรงกับไฟล์ใด ห้ามใช้ผลอ่าน source แทนหลักฐานของ firmware ที่กำลังรัน

อย่าเริ่มจากข้อสรุปว่า native USB ต้องหลุดทุกครั้งที่รีเซ็ต หรือการเปิดพอร์ตทุกครั้งต้องรีเซ็ตบอร์ด ขึ้นกับชนิดรีเซ็ต การตั้งค่า และการเปลี่ยน DTR/RTS เสียงแจ้งเตือน Windows อย่างเดียวไม่ระบุสาเหตุ

## 1. ให้มีผู้ใช้พอร์ตเพียงโปรแกรมเดียว และเปิดค้างระหว่างใช้งาน

1. ตรวจเส้นทางที่เปิดพอร์ตจริง ได้แก่ dashboard, PlatformIO Serial Monitor และสคริปต์ตรวจ/แฟลชที่เกี่ยวข้อง รายงานสิ่งที่ตรวจพบ อย่าฆ่า process แบบเหมารวม
2. ให้ dashboard มี SerialWorker เจ้าของ connection เพียงตัวเดียว การกดปุ่มหรือส่งคำสั่งแต่ละครั้งต้องใช้ connection เดิม ไม่เปิด/ปิดพอร์ตใหม่
3. แยกช่วง upload ออกจากช่วงใช้งาน ก่อน upload ปิด connection ของโปรแกรมที่ถือพอร์ตอย่างเรียบร้อย หลัง upload ให้มีผู้เปิดพอร์ตเพียงตัวเดียว
4. Reconnect เฉพาะเมื่อมีหลักฐานว่า connection ใช้งานไม่ได้ ไม่สั่งรีเซ็ตหรือแฟลชเพื่อทดลองวน หากไม่มีข้อมูลชั่วคราว ห้ามถือว่าเป็นเหตุให้ reconnect ทันที
5. ตรวจพฤติกรรมเมื่อพอร์ตหาย: dashboard ต้องไม่ค้าง ไม่ retry ถี่จนสร้างปัญหาเอง และไม่เล่นคำสั่ง Scan/Collect/Analyze ที่หมดอายุข้าม session กลับมาโดยไม่ตั้งใจ ใช้ ACK/session/duplicate protection เดิม ไม่รื้อ protocol
6. บันทึกเวลาและเหตุการณ์ `open_attempt`, `open_success`, `close`, `read_error`, `write_error`, `reconnect` พร้อมเหตุผลและชื่อพอร์ต ห้าม log วนทุกครั้งที่อ่านได้ข้อมูลว่าง

## 2. เก็บหลักฐานรีเซ็ตและทดสอบแยกสาเหตุ

### ข้อมูลที่ต้องเห็น

- Firmware identifier ที่ระบุ build และ environment ได้จริง
- Boot/session ID ที่คงเดิมตลอดการบูตหนึ่งครั้ง ใช้ของเดิมถ้ามี
- Reset reason ทั้งค่าดิบและคำอธิบายที่ตรงกับ enum ของ SDK ที่ติดตั้ง ห้ามตีความเหตุที่ไม่รู้จักเอง
- Uptime และหมายเลข heartbeat ทุกประมาณ 1–2 วินาที
- ขั้นตอนปัจจุบัน เช่น `serial_ready`, `spi_ready`, `panels_initialized`, `loop_running` ให้หมายถึงตำแหน่งที่โค้ดผ่าน ไม่ใช่ยืนยันว่าจอแสดงภาพสำเร็จ

ส่งข้อมูลในรูปแบบที่ parser ของแต่ละ environment รองรับ อย่าแทรกข้อความดิบจน dashboard อ่าน JSON ไม่ได้ ให้ข้อมูลสำคัญปรากฏซ้ำหรือเรียกดูได้หลัง reconnect เพราะข้อความแรกตอน boot อาจหายไปก่อน host พร้อมอ่าน

เฟิร์มแวร์ต้องรันได้โดยไม่มี host เปิดพอร์ต ห้ามเพิ่ม `while (!Serial)` แบบรอไม่สิ้นสุด ตรวจทั้ง write และ flush ไม่ให้ telemetry กลายเป็นจุดที่ทำให้ลูปหยุด หากใช้ LED heartbeat ให้บอกเพียงว่าโค้ดผ่านจุดนั้น ห้ามเขียนว่าไฟเขียวรับรองไฟเลี้ยงและจอทั้งหมดปกติ

### การทดสอบบนบอร์ด

ยืนยัน environment และ firmware ID ที่ใช้ก่อนทดสอบ แฟลชเฉพาะเมื่อ binary จำเป็นต้องเปลี่ยน ไม่แฟลชซ้ำทุกครั้งที่เปิดพอร์ต คงสายและโหลดจอเหมือนเดิมตลอดการเปรียบเทียบชุดแรก

| รอบ | วิธีทดสอบ | หลักฐานที่ต้องเก็บ |
| --- | --- | --- |
| A | หลังเริ่มเฟิร์มแวร์ ปล่อย 5 นาทีโดยไม่มีโปรแกรมเปิด COM | USB ปรากฏ/หายเมื่อไร และ LED heartbeat ถ้ามี ใช้การดูรายการอุปกรณ์ที่ไม่เปิด COM |
| B | เปิด diagnostic logger เพียงครั้งเดียวแล้วค้าง 5 นาที | เหตุการณ์เปิดพอร์ต, boot/session, reset reason, uptime และช่วงข้อมูลขาด |
| C | ปิด logger แล้วเปิด dashboard เพียงตัวเดียว ใช้งาน 10 นาที กดปุ่มควบคุมตามปกติ | จำนวน reconnect/reset, การตอบคำสั่ง, ACK และอาการ UI ค้าง |
| D | เมื่อ B เสถียรแล้ว ทดลองปิดและเปิด connection แบบควบคุม 3 รอบ เว้นช่วงอย่างน้อย 10 วินาที | การเปิด/ปิดแต่ละครั้งทำให้ session เปลี่ยนหรือไม่ เกิด USB หายตอนไหน |

ถ้ารอบใดหลุดซ้ำจนได้หลักฐานชัด ให้หยุดรอบนั้นและวิเคราะห์ก่อน ไม่ต้องฝืนครบเวลาหรือเปิดปิดหลายสิบครั้ง ระหว่างรอรายงานความคืบหน้าได้ แต่ไม่เปิด serial ตัวที่สองเพื่อดูสถานะ

### กติกาการตีความ

- Session เปลี่ยนและ uptime เริ่มใหม่: มีหลักฐานการบูตใหม่ ใช้ reset reason ประกอบ ไม่เดาว่าไฟตกจากเสียง Windows
- USB หายแล้วกลับมา แต่ session เดิมและ uptime เดินต่อสอดคล้องเวลาที่ผ่านไป: สนับสนุนว่าแอปบนบอร์ดไม่ได้เริ่มใหม่ ให้ตรวจ USB/host ต่อ
- หลุดในรอบ A: การเปิด/ปิดพอร์ตจากแอปไม่เพียงพอจะอธิบาย ต้องตรวจสาเหตุอื่นต่อ
- ไม่มีข้อมูลหลังหลุด: ให้รายงานว่าแยกสาเหตุไม่ได้ ห้ามตีความความเงียบว่าเฟิร์มแวร์หยุดแน่นอน
- ถ้าพบ crash, watchdog หรือ brownout ให้เก็บหลักฐานและเสนอขั้นต่อไปเฉพาะสาเหตุนั้น ไม่เพิ่มการ reconnect เพื่อซ่อนปัญหา

## 3. ตรวจ DTR/RTS และการจัดการพอร์ตให้ตรงกัน

1. อ่าน `_open()` และเครื่องมือที่ใช้จริงก่อนแก้ ค่าเริ่มต้นของ dashboard ตอนร่างใบนี้คือ `DTR=True / RTS=False` อย่าเปลี่ยนเป็น False ทั้งคู่โดยเดาว่าต้องดีกว่า
2. ระบุค่าที่ใช้ให้ชัดสำหรับ diagnostic logger และ PlatformIO Monitor ใช้ค่าเดียวกับ dashboard เป็น baseline (`monitor_dtr=1`, `monitor_rts=0` หากใช้ Monitor) ตรวจ syntax กับ PlatformIO ที่ติดตั้ง และใช้กับ environment ที่ทดสอบจริง
3. แยก DTR/RTS ของการ monitor ออกจาก reset sequence ที่ esptool ใช้ upload ไม่รื้อกลไกเข้า download mode เพื่อแก้ปัญหาเปิด monitor
4. ตรวจว่ามีการเปลี่ยน DTR/RTS หลัง `open()` หรือจาก reconnect หรือไม่ เอาการสั่ง reset ที่ไม่จำเป็นออก แต่ไม่อ้างว่าการ preset ค่าแก้ glitch ของทุก OS/driver ได้แน่นอน
5. ตรวจ timeout ทั้งการอ่านและเขียน การส่งจาก dashboard ต้องไม่ทำให้ UI รอไม่สิ้นสุด รักษาระบบคิวและสถานะคำสั่งให้ถูกต้องเมื่อเขียนล้มเหลว
6. ถ้าจะเปลี่ยนค่าทดลอง ให้เปลี่ยนทีละปัจจัยและเทียบ boot/session จากรอบ D ไม่เปลี่ยน USB mode, baud, reset sequence และเฟิร์มแวร์พร้อมกัน
7. แก้คอมเมนต์ที่อ้างว่าเปิดพอร์ตแล้วต้องรีเซ็ต หรือ DTR จำเป็นเสมอ ให้แยกสิ่งที่เอกสารระบุออกจากผลที่วัดกับเครื่องนี้

## การตรวจและเกณฑ์ส่งมอบ

- รัน tests ที่เกี่ยวข้องกับ serial lifecycle/protocol; ตรวจเพิ่มเฉพาะพฤติกรรมที่แก้ เช่น connection ไม่ถูกเปิดใหม่ทุกคำสั่ง, exception แล้ว UI ไม่ค้าง และ telemetry ไม่ทำให้ parser พัง
- Build environment ที่แก้ หากเปลี่ยนทั้ง main และ diag ให้ build ทั้งสอง ไม่ต้อง buildfs หากไม่ได้แก้ filesystem/assets
- ทดสอบจำลองให้รายงานเป็นผลจำลองเท่านั้น การ build ผ่านไม่ใช่ USB ผ่าน
- เกณฑ์เสถียรเบื้องต้น: รอบ B และ C ไม่มี reset หรือ USB หลุดโดยไม่คาดหมาย, dashboard ใช้งานต่อเนื่องได้ และรอบ D ระบุผลเปิด/ปิดแต่ละครั้งได้จากหลักฐาน
- ถ้ายังไม่มีบอร์ดให้ทดสอบ ส่งโค้ดพร้อม build/tests และระบุรอบฮาร์ดแวร์ว่า `NOT RUN` อย่าเติม `PASS`
- ถ้าทดสอบแล้วไม่ผ่าน ส่ง raw log และสาเหตุที่มีหลักฐานรองรับ พร้อมการทดลองถัดไปหนึ่งข้อ ไม่จำเป็นต้องฝืนสรุปว่าซ่อมสำเร็จ

ส่งรายงานที่ `prototype-v1/output/claude-usb-stability-status.md` และ log ใน `prototype-v1/output/usb-stability/` ระบุไฟล์ที่แก้, environment/build ID, พอร์ตที่พบจริง, DTR/RTS ที่ใช้, เวลาทดสอบ, จำนวน reset/reconnect และข้อจำกัดค้างอยู่ ปิดท้ายด้วยขั้นตอนให้ผู้ใช้เปิดใช้งานที่สั้นและทำตามได้
