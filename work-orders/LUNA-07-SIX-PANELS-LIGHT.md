ผู้สั่งงาน: Claude (แม่งาน ตรวจรับงาน) · ผู้ทำ: **Codex Luna** (เขียนโค้ด build แฟลช เปิด monitor และเทสเอง)
ผู้ช่วยค้นข้อมูล: Codex Astra ใช้เมื่อข้อมูลหนักจริงเท่านั้น งานนี้ไม่น่าต้องใช้
วันที่: 17 กันยายน 2026 · รันทุกคำสั่งจาก `prototype-v1/`

## 1. เป้าหมาย (ขอบเขตแคบ)

จอ ST7789 240×240 **ทั้ง 6 ใบติดพร้อมกัน** บน ESP32-S3-Zero ตัวเดียว
แต่ละใบแสดงสีพื้น ชื่อหน้า และเลข CS แล้ววนเปลี่ยนสี **แค่นั้น**

**ไม่ทำในงานนี้:** ภาพทะเล, atlas, เป้าเล็ง, dashboard, เสียง, ปุ่ม/ล้อ, การเร่งความเร็ว SPI, การเปิด `nz` ในฉากทะเล
(`kDisplayEnabled[5]` คงเป็น `false` ไว้ก่อน เป็นงานถัดไปหลังงานนี้ผ่าน)

## 2. ใช้ทางที่เคยทำให้จอติดจริง — sweep mode ของเฟิร์มแวร์หลัก

คืนวันที่ 13 ก.ย. 2026 (ราว 22:49) จอติดครั้งแรกหลังแก้สาย ด้วย **environment `esp32-s3-zero` + `kPanelSweepTest = true`**
ไม่ใช่ env `diag` ซึ่ง**ยังไม่เคยพิสูจน์บนฮาร์ดแวร์** และไม่มีชุดคำสั่งเปิดจอซ้ำ — **งานนี้ห้ามใช้ `diag`**

ทำไม sweep mode (`setupSweepDisplays()` / `paintSweep()` ใน `firmware/src/main.cpp`) ถึงเหมาะ:
- init **ทุก CS ใน `kCs`** ไม่สน `kDisplayEnabled` ไม่แตะ atlas/renderer
- `init()` ของไลบรารีวิ่งที่ความเร็วของมันเอง จึง**ยิงชุดคำสั่งเปิดจอซ้ำที่ 4 MHz** (`kSweepSpiClockHz`) — SWRESET → SLPOUT → COLMOD 0x55 → NORON → DISPON
- เปิด inversion ตาม `kFaces[i].inversion` (ทุกหน้า `true`)
- ทุกรอบส่ง SLPOUT + DISPON ซ้ำ จอที่รับไบต์เพี้ยนจึงฟื้นเองได้
- ไม่ต้องต่อโน้ตบุ๊ก เสียบหัวชาร์จแล้วดูจอได้เลย

## 3. ข้อเท็จจริง — ผู้ใช้ยืนยันแล้ว 17 ก.ย. 2026

| เรื่อง | ค่า |
|---|---|
| จอ | **มีครบ 6 ใบ** (ซื้อใบที่ 6 มาแล้ว) |
| CS ใบที่ 6 (`nz`) | **GPIO7** |
| ไฟ VCC จอ | **ขา 3V3 ของบอร์ด ESP32** (ไม่ใช้ MP1584 — ห้ามต่อสองแหล่ง) |
| บัสร่วม | SCK=12, MOSI=11, DC=9, RST=10 |
| CS 5 ใบเดิม | px=8, nx=13, py=4, ny=5, pz=6 |
| BL | ไม่ต่อ |
| แฟลช | `upload_speed = 115200` + `--no-stub` ห้ามถอด · Serial DTR=1, RTS=0 · เช็ค COM ใหม่ทุกครั้ง |
| **อนุญาตแฟลช** | **ผู้ใช้อนุญาตแล้ว 17 ก.ย.: เทส + build ผ่านแล้วแฟลชทิ้งไว้บนบอร์ดได้ทันที** ผู้ใช้จะเสียบจอและเทสสายเอง |
| AS5600 (เฟสถัดไป) | SDA = GPIO1, SCL = GPIO2 — **จองไว้** งานนี้ห้ามขับสองขานี้ · ยังไม่ต้องเขียนโค้ดเซนเซอร์ |
| การหมุน | ไม่ใช้ slip ring · หมุนได้ราว 270° หรือจนสายตึง |

**สาเหตุที่จอเคยไม่ติด (จากแชท 13 ก.ย. ยืนยันด้วยการวัด)** — แก้พร้อมกันหลายอย่าง จึงชี้ตัวการเดียวไม่ได้:
1. สาย SDA กับ DC ไฟไปไม่ถึงปลายฝั่งจอ → เปลี่ยนสายจัมเปอร์แล้วหาย
2. เบรดบอร์ด/ชุดสายรวมหน้าสัมผัสไม่ดี → เปลี่ยนเบรดบอร์ดแล้วจอขึ้น
3. ที่ 10 MHz ภาพซ่าเป็นกริดสี (ตอนนั้นสายยังเสีย) → ลดเหลือ 4 MHz
4. `init()` ไม่ใช้ความเร็วที่ตั้ง → ยิงคำสั่งเปิดจอซ้ำที่ 4 MHz
5. สีกลับ (ปลาฟ้า ทะเลส้ม) → เปิด inversion
6. บอร์ด "เงียบ" เป็นบั๊กฝั่งคอมที่เปิดพอร์ตโดยไม่ยก DTR ไม่ใช่บอร์ดเสีย

ข้อที่**ผิด อย่าเชื่อ**: "SDA กับ RST ช็อตกัน" (RST 3.3V มาจาก pull-up ในโมดูลจอ), "สายยาวทำให้จอพัง"
รายละเอียดเต็ม: `docs/display-bringup-findings.md`

## 4. งานโค้ด

1. **เปลี่ยน CS ของ `nz` จาก 17 เป็น 7 ให้ตรงกันทุกที่**
   - `firmware/include/deep_sphere_config.h`: `kCs[5]` และ `kFaces[5].cs` · แก้คอมเมนต์ที่บอกว่า nz ไม่มีจอ/GPIO7 ว่าง ให้ตรงความจริง
   - `config/faces.json`, `config/board.json` และไฟล์ config อื่นที่ `tests/test_config_agreement.py` ผูกไว้ (ให้ grep หา `17` ที่เป็น CS ของ nz)
   - `config/wiring-table.md` แถว GPIO7 และ GPIO17
2. **ขา GPIO7 ถูกใช้ซ้ำในโค้ด ต้องเคลียร์ให้หมด**: `kSparePin = 7` (pin test ขับขานี้สวนทาง) และ `kButtonAnalyzeRecommended = 7`
   ทำให้ pin test ไม่ขับ GPIO7 ทับ CS ของจอ (เช่นตั้ง spare เป็น `-1` แล้วข้ามถ้าเป็น -1) · บันทึกว่าตอนนี้ไม่มีขาสำรองแล้ว
3. ตั้ง `kPanelSweepTest = true` · **ไม่แตะ** `kSweepSpiClockHz` (4 MHz), ชุดคำสั่งเปิดจอ, inversion, `kDisplayEnabled`
4. ถ้าพบว่า sweep mode ใช้ `kDisplayCount` หรือ array ขนาด 6 แบบที่ nz ถูกข้าม ให้แก้เท่าที่จำเป็นให้ครบ 6 และรายงาน
5. เทสที่ fail อยู่ก่อนแล้ว `test_only_enabled_faces_are_initialized` **ไม่ใช่งานนี้ ห้ามแก้** · เทสอื่นต้องไม่พังเพิ่ม
6. **คำสั่งหาสายหักต้องใช้ได้ขณะเฟิร์มแวร์อยู่ใน sweep mode** โดยไม่ต้องแฟลชใหม่: `hold_pin` (ยกไฟทีละขาเท่านั้น) และ `scan_shorts` ใน `main.cpp`
   ถ้า sweep mode ไม่อ่านคำสั่ง serial ให้ทำให้อ่านได้ และระหว่าง `hold_pin` ให้หยุดวาดจอชั่วคราว (ไม่งั้นขา SPI แกว่งทับค่าที่วัด) · มีคำสั่งกลับไปวาดต่อ
   ลิสต์ขาของ pin test / `scan_shorts` ต้องมี CS ครบ 6 และ **ไม่มี GPIO1/2**
7. `config/wiring-table.md`: จอง GPIO1 = AS5600 SDA, GPIO2 = AS5600 SCL · ปุ่มจริง Scan/Collect ไม่ใช้แล้ว (ย้ายไป numpad) — แก้แค่เอกสาร ไม่แก้ค่าคงที่ปุ่มในโค้ดงานนี้
8. เขียน **ใบผังขาสำหรับผู้ใช้** `output/pin-sheet-6-panels.md`: ตารางจอใบที่ 1–6 × ขาโมดูล `GND VCC SCL SDA RST DC CS BL` → ขาบอร์ด และแถว AS5600 แยกไว้ท้าย ภาษาง่าย พิมพ์ติดโต๊ะได้

## 5. ลำดับเทส (Luna รันเอง ผู้ใช้เสียบสายและดูจอ)

ก่อนเริ่ม: ปิด dashboard และ serial monitor อื่น (พอร์ตเปิดได้ทีละโปรแกรม)

```text
.venv\Scripts\python -m unittest discover -s tests -t tests
.venv\Scripts\python -m platformio run -e esp32-s3-zero
.venv\Scripts\python -m platformio run -e esp32-s3-zero -t upload --upload-port COMx
.venv\Scripts\python -m platformio device monitor -e esp32-s3-zero --port COMx
```

เฟิร์มแวร์ init ครบ 6 CS เสมอ จอที่ยังไม่เสียบไม่เป็นอันตราย → **แฟลชครั้งเดียว** แล้วเพิ่มจอทีละใบ ไม่ต้องแฟลชซ้ำ

| ขั้น | ทำ | ดูอะไร |
|---|---|---|
| 0 | เทส + build | build SUCCESS · ไม่มีเทส fail เพิ่มจากเดิม |
| 1 | ต่อ **จอใบที่เคยติด** ใบเดียว แฟลช เปิด monitor | จอมีสี + ชื่อหน้า + เลข CS · log `sweep initialized face .. on CS..` ครบ 6 บรรทัด |
| 2–6 | **ถอดไฟก่อน** → เพิ่มจอ 1 ใบ → เสียบไฟ (ใบ `nz` ต้องขึ้น `CS7`) | ใบใหม่ติด ใบเก่า**ไม่ดับ** · สีไม่กลับ |
| 7 | ครบ 6 ใบ ปล่อยวน **5 นาที** | ไม่มีใบดับ/ซ่า · แถบดำกระโดดทุกรอบ (ถ้าค้างแปลว่าจอค้าง) |
| 8 (ถ้ามีมิเตอร์) | วัด VCC ที่จอใบไกลสุดตอนติดครบ 6 | บนย่าน V · กระแสรวมต้องวัด**ย่าน mA** เท่านั้น |

- **ห้ามเสียบ/ถอดจอขณะมีไฟ**
- ไฟจอมาจาก 3V3 ของบอร์ด ซึ่ง**ยังไม่เคยพิสูจน์ว่าพอสำหรับ 6 ใบ** ถ้าพอร์ตโน้ตบุ๊กไม่นิ่ง (พอร์ตหาย, บอร์ดรีบูต, จอวูบ) ให้ย้ายสาย USB ของบอร์ดไปหัวชาร์จผนัง แล้วอ่านผลจากจอแทน log · บันทึกว่าขั้นไหนไม่มี log
- Luna มองไม่เห็นจอ **ถามผู้ใช้ทุกขั้นว่าเห็นอะไร** แล้วจดตามจริง

## 5.5 หาสายหักในชุดสายรวม (ผู้ใช้ทำ Luna คุมคำสั่ง)

1. **ดูจากจอก่อน:** ใบเดียวดำ = กิ่งของใบนั้น (CS/VCC/GND) หรือตัวจอ · ทุกใบดำ = สายร่วม (SCK/MOSI/DC/RST/VCC/GND ช่วงลำต้น)
2. **สลับจอ:** ย้ายจอที่ติดแน่ไปเสียบตำแหน่งที่ดำ ถ้ายังดำ = สาย ถ้าติด = จอใบเดิมเสีย
3. **ขยับสาย (wiggle):** ระหว่างวน ผู้ใช้บีบ/งอชุดสายทีละช่วง ถ้าจอกระพริบหรือดำตอนงอช่วงไหน = หักช่วงนั้น
   (sweep ส่ง SLPOUT/DISPON ซ้ำทุกรอบ จอที่หลุดชั่วคราวจะกลับมาเอง จึงเห็นเป็นกระพริบ)
4. **วัดทีละเส้น:** Luna สั่ง `hold_pin` ทีละขา ผู้ใช้วัดที่**ปลายสายฝั่งจอ**ด้วยย่าน V: ขาที่ยก = ~3.3V, ขาอื่นในชุด = ~0V
   ขาที่ยกแต่ปลายได้ 0V = สายขาด · ขาที่ไม่ได้ยกแต่ปลายได้ 3.3V = ต่อผิดขา/ลัด
   ⚠️ RST ปลายจออ่านได้ 3.3V ตลอดเพราะ pull-up ในโมดูล **ไม่ใช่ช็อต** (เคยเดาผิดมาแล้ว)
5. บันทึกผลเป็นตาราง `เส้น | ขาบอร์ด | ปลายจอใบไหน | ค่าที่วัด | สรุป`

## 6. แยกอาการ (เปลี่ยนทีละตัวแปรเท่านั้น)

| อาการ | น่าจะเป็น | ทำต่อ |
|---|---|---|
| ใบเดียวไม่ติด ใบอื่นติด | CS / VCC / GND ของใบนั้น หรือตัวจอ | สลับจอใบนั้นไปตำแหน่งที่ติดแน่ → แยกสายกับจอ |

| ใบ `nz` ไม่ติดใบเดียว | GPIO7 ไม่ถึง หรือยังมีโค้ดขับ GPIO7 ทับ | เช็คข้อ 4.2 ก่อน แล้วจึงให้ผู้ใช้วัดสาย |
| ใบเก่าดับตอนใบใหม่ขึ้น / บอร์ดรีบูต | ไฟ 3V3 ตก | ย้ายไปหัวชาร์จผนัง / วัดแรงดัน · ไม่แก้โค้ด |
| ทุกใบดำ | สายร่วม SCK/MOSI/DC/RST หรือเฟิร์มแวร์ไม่ได้อยู่ใน sweep mode | ดู log ว่ามี `sweep initialized` ไหม |
| เพิ่มถึงใบหนึ่งแล้วเริ่มซ่า | บัสรับโหลดไม่ไหว | รายงานว่าใบที่เท่าไร · ทางแก้ที่เคยเสนอ: สายสั้นลง + R 22–33 Ω ที่ SCK (ผู้ใช้ตัดสินใจ) · **ห้ามลดความเร็วเอง** |
| สีกลับ | inversion | รายงานพร้อมใบที่เป็น |

## 7. ส่งงาน

เขียน `output/luna-07-six-panels-status.md` สั้น ๆ:

1. ผลเทส + build + path log แฟลช/monitor ที่เก็บใน `output/`
2. ตาราง 6 แถว: `หน้า | CS | ติดไหม | สีถูกไหม | ขั้นที่ติด | หมายเหตุ`
3. ไฟล์ที่แก้ทั้งหมด และจุดที่ GPIO7 เคยถูกใช้ซ้ำ แก้อย่างไร

5. **แยก 3 กลุ่ม:** เห็น/วัดจริง · ผู้ใช้บอก · ยังไม่ได้ตรวจ — ห้ามยืนยันเกินหลักฐาน

**ไม่ผ่านแต่ส่งงานได้** = รายงานตามจริงว่าติดกี่ใบ ขั้นไหน อาการเข้าแถวไหนในข้อ 6 — ห้ามแก้โค้ดวนไปเรื่อย ๆ เพื่อไล่ปัญหาสาย
