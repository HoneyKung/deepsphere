# LUNA-05 — ใบส่งต่อให้ Astra

เขียน 11 กันยายน 2026 ตอนตี 4 ต่อจาก LUNA-04 ผู้ใช้ติดเดดไลน์ จึงหยุดไล่บั๊กแล้วส่งต่อ

---

## 1 สิ่งที่ผู้ใช้ต้องการต่อจากนี้ — เปลี่ยนทิศทางงานภาพ

**ไม่เอาภาพทะเลแบบภาพถ่าย/พาโนรามานิ่งที่ LUNA-04 ทำไว้** ผู้ใช้บอกชัดว่าตอนนี้ยังไม่ได้ทำตัวเต็ม
สิ่งที่ควรเห็นในต้นแบบคือ **ระบบที่ขยับได้จริง** ไม่ใช่ภาพสวย

ต้องการ:

- ภาพ **วาดด้วยโค้ด** ไม่ใช่ raster ที่เตรียมไว้ล่วงหน้า
- **ไล่เฉดสีลงไปเรื่อย ๆ ตามความลึก** ยิ่งลงยิ่งมืด เห็นการเปลี่ยนชั้นชัด
- แต่ละชั้นมี **เอฟเฟกต์ ปลา ฟองอากาศ ที่สมกับชั้นนั้น**
- กด **ขึ้น/ลงแล้วเปลี่ยนชั้นได้เห็นชัด**
- **สิ่งมีชีวิตวิ่งผ่านจอ** ไม่ใช่อยู่นิ่ง
- **สแกนได้จริง** กับตัวที่กำลังวิ่งอยู่

### สิ่งที่ต้องรื้อเพราะทิศทางนี้

ท่อภาพปัจจุบันเป็น atlas นิ่ง 1024x512 RGB565 โหลดเข้า PSRAM ครั้งเดียวแล้ว sample ต่อพิกเซล
ซึ่ง **รองรับสิ่งมีชีวิตที่ขยับไม่ได้เลย** ต้องออกแบบใหม่เป็น renderer ต่อเฟรมบนบอร์ด:

- พื้นหลัง = ฟังก์ชันของ (ทิศของพิกเซล, depth) คำนวณสด ไม่ต้องมี atlas
- สิ่งมีชีวิต = sprite ที่มีตำแหน่งอัปเดตตามเวลา
- `targets.json` เลิกเป็นตาราง UV นิ่ง ต้องเป็น hit test กับตำแหน่งสิ่งมีชีวิต ณ วินาทีที่กดสแกน

### ข้อจำกัดที่ต้องออกแบบรอบ ๆ

จอ 5 ใบ x 240x240 x 2 ไบต์ = **576 KB ต่อการรีเฟรชครบหนึ่งรอบ** บัสเดียวที่ 24 MHz
วาดใหม่ทั้งหมดทุกเฟรมไม่ไหว ต้องใช้ dirty rectangle — วาดทับเฉพาะกรอบของ sprite กับพื้นหลังตรงนั้น
เหมือนที่ `renderReticleMove()` ทำกับเป้าเล็งอยู่แล้ว ใช้เป็นแบบได้

กฎเดิมที่ยังต้องรักษา: **ภาพที่ preview บนคอมกับที่บอร์ดวาด ต้องมาจากการคำนวณชุดเดียวกัน**
ตอนนี้ทำได้ด้วย `tools/atlas_math.py` คู่กับ `firmware/src/math/cube_math.cpp` และมี vector test
1413 ข้อคุมอยู่ ถ้าเขียน renderer ใหม่ ต้องคง pattern นี้ไว้

## 2 บั๊กฮาร์ดแวร์ที่ยังไม่จบ — เรื่องด่วนที่สุด

### อาการ

- ต่อจอ 5 ใบแล้ว **ขึ้นภาพแค่ใบเดียว คือใบที่ CS = GPIO6 (`pz`)**
- ใบที่ CS = GPIO8 (`px`) ซึ่ง**เคยขึ้นภาพทดสอบลูกศรได้ตอนเทสจอเดียว ตอนนี้ไม่ขึ้น**
- บอร์ดค้าง/หลุดหลังจากนั้น

### ตัดออกไปได้แล้ว ไม่ต้องไล่ซ้ำ

- **สายที่ใช้ร่วมกัน SCK12 / MOSI11 / DC9 / RST10 ไม่ผิด** เพราะ `px` เคยวาดได้ผ่านสายชุดนี้
- **ท่ออัปโหลดไม่ผิด** แฟลชผ่านแล้ว hash ตรงทั้ง firmware และ littlefs
- **แผงคอมไม่ได้รีเซ็ตบอร์ดแล้ว** พิสูจน์แล้วว่าเปิดปิดพอร์ตสองรอบได้ session เดิม seq เดินต่อ
- **เฟิร์มแวร์ตั้งค่าถูก** `kSingleDisplayTest=false`, `kDisplayEnabled={t,t,t,t,t,false}`,
  `kHardwarePinsConfirmed=true` สิ่งที่วาดคือ `renderScene()` ไม่ใช่ภาพทดสอบแล้ว

### สมมติฐานที่เหลือ เรียงตามน้ำหนัก

1. **ไฟไม่พอ** จอ 5 ใบกินไฟจากขา 3V3 ของบอร์ดผ่าน USB คอมเส้นเดียว
   ค่า 10 mA ต่อใบที่วัดไว้ **เชื่อไม่ได้** เพราะอ่านจากช่วง 10 A ซึ่งละเอียดแค่ 0.01 A หนึ่งหลัก
   และผู้ใช้เคยสังเกตเองว่าตอนจ่ายจากหัวชาร์จมันนิ่ง ตอนจ่ายจากคอมมันหลุด
   **ให้วัดใหม่ที่ช่วง mA ก่อนทำอย่างอื่น**
2. **สาย CS** วัดความต่อเนื่องจากแพด CS ของแต่ละใบไปยัง GPIO ที่ถูกต้อง และเช็คว่าไม่มี CS สองเส้นช็อตกัน
   ผังปัจจุบัน: px=8, nx=13, py=4, ny=5, pz=6, nz=17 (ไม่มีจอ)
3. **จอบางใบเสีย** เคยมีใบหนึ่งไหม้ไปแล้ว อย่าตัดความเป็นไปได้ว่ามีใบอื่นเสียอีก

### วิธีไล่ที่แนะนำ

ไล่ทีละใบ ตั้ง `kDisplayEnabled` ให้เหลือ true ตัวเดียวแล้วแฟลช ยืนยันว่าจอใบนั้นกับสาย CS เส้นนั้นดี
ก่อนเปิดเพิ่มทีละใบ

**ควรเพิ่มโหมดไล่จอแบบไม่ต้องแฟลชซ้ำ**: คำสั่ง serial ที่สั่งวาดสีทึบ + ชื่อหน้า ลงทีละใบวนไป
จะประหยัดเวลากว่าการแฟลชใหม่ทุกครั้งมาก

## 3 บั๊กแผงคอมที่แก้ไปแล้วในรอบนี้ — อย่าทำซ้ำ

| ที่ | อาการเดิม | แก้เป็น |
|---|---|---|
| `platformio.ini` | อัปโหลดตายที่ `Changing baud rate to 460800` และที่ stub loader | ปัก `upload_speed = 115200` และ `upload_flags = --no-stub` เพราะบอร์ดแฟลชผ่าน USB Serial/JTAG ในตัวชิป |
| `SerialWorker._open` | pyserial ยก DTR/RTS ตอนเปิดพอร์ต ซึ่ง USB stack ของชิปอ่านว่าเป็นคำสั่งรีเซ็ต บอร์ดจึงรีบูตทุกครั้งที่แผงคอมกดต่อ | กด DTR/RTS ลงก่อน `open()` |
| `SerialWorker.run` | พอร์ตหลุดทีเดียว thread ตายถาวร | วนต่อกลับเองทุก 1 วินาที |
| `SerialWorker._pump` | `readline()` บนพอร์ตที่ timeout คืนบรรทัดครึ่งเดียว ทำให้ parse error รัว | บัฟเฟอร์ไบต์แล้วตัดที่ newline เอง |
| `firmware gSession` | สร้างจาก MAC + `millis()` ซึ่งซ้ำกันข้ามการรีบูต แล้ว `EventDeduper` ทิ้ง event ของ session ใหม่ว่าเป็นของซ้ำ | เติม `esp_random()` |
| `app.drain_events` | ทุก state ที่เข้ามาสั่ง repaint UI เต็มหนึ่งครั้ง บอร์ด heartbeat หลายครั้งต่อวินาที หน้าต่างเลยขึ้น Not Responding ทันทีที่ต่อบอร์ดจริง | ดูดคิวให้หมดก่อนแล้วค่อย repaint ครั้งเดียว |

**ข้อสุดท้ายยังไม่ได้ทดสอบกับบอร์ดจริง** เพราะบอร์ดหลุดไปก่อน ให้ยืนยันก่อนเชื่อ

## 4 สิ่งที่ยืนยันแล้วและควรเก็บไว้

- เรขาคณิตหกหน้าและ mount math ผ่าน native 1413 checks
- ชั้น reticle แยกจากภาพพื้นหลัง
- โปรโตคอล Scan / Collect / Analyze และที่เก็บ sample ใน `output/samples/` มีของเก่า 23 ชุด **ห้ามลบ**
- คีย์บอร์ด: numpad `1` `2` `3` = Scan / Collect / Analyze, `Up` `Down` = ความลึก, `Left` `Right` = มุมหันครั้งละ 5 องศา
- **ความลึกเลื่อนได้อิสระ** ผู้ใช้ตัดสินแล้ว 11 ก.ย. 2026 ไม่มีด่านหาปากทางลง ดู `00-open-issues.md` §3.2
- คอนฟิกจอ 5 ใบ หน้าล่าง `nz` ไม่มีจอ
- ไม่มีเซนเซอร์วัดการหมุน ล้อ KY-040 ไม่มีขาแล้วเพราะ GPIO4/5/6 ไปเป็น CS
- `GPIO19/20` เป็นคู่ข้อมูล USB ห้ามใช้
- Python 75 passed, native 1413 checks ณ เวลาส่งต่อ

## 5 ที่ยังไม่มีใครตอบ

- ผลตรวจเดิม: **ไม่มีมุมหันคงที่ค่าใดเข้าถึง subject ได้เกิน 2 จาก 6 ตัว** ดู `output/heading-reachability.json`
  ถ้า renderer ใหม่วางสิ่งมีชีวิตเอง ปัญหานี้หายไปเอง แต่ต้องออกแบบให้สิ่งมีชีวิตวิ่งผ่านหน้าที่มีจอจริง ไม่ใช่หน้าที่ปิดอยู่
- ความอ่านออกบนจอจริง 30 มม. ยังไม่มีใครยืนยันด้วยตา
